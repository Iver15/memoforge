## §0. Рамка

### 0.1. Диагноз (почему редизайн, а не патч)

1. **Оркестратор — LLM, читающий за Full-прогон ≈70–110k токенов инструкций** (метод базлайнового аудита `bytes/4` даёт 95–110k; контрольный `wc -w` ≈54k слов ≈70–75k; 3 резидентных файла, 17 файлов фаз, 12 demand-контрактов ≈40k из которых 8–10 читаются практически всегда, `continue/SKILL.md` ≈14k) и выполняющий ≈250–300 «служебных» tool-вызовов ради ≈20 содержательных диспатчей (01 §1.2–1.3). ≈165 императивных вхождений (`MUST|MANDATORY|HARD RULE|NEVER|Do NOT|do not`), из них строго MUST/NEVER/HARD RULE ≈73.
2. **12 задокументированных инцидентов (01 §4.1): 9 из 12 — пропуск LLM бухгалтерского шага → усиление прозы → следующий пропуск; 3 — дефекты инфраструктуры** (хук с `${CLAUDE_PLUGIN_ROOT}` на Windows, matcher `^WebFetch$`, ложноположительная проба v0.2.0) — они закрываются §8, а не §3. Автор сам зафиксировал предел прозы при удалении Lessons Studio: «any future re-introduction needs a non-prompt-resident enforcement mechanism» (`CHANGELOG.md:81` ✓).
3. **Платформа ушла из-под ног** (04 §Верификация, 06 §1): Cowork Live artifacts отключены 19.08.2026 → весь live-progress-стек (`mcp__cowork__create_artifact/update_artifact`, `render_live_progress.py`, 15 секций «Live progress» в агентах) мёртв; `TodoWrite` не выдаётся на Sonnet 5 / Fable 5 без `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`; `visualize` MCP нестабилен; ограничение «субагенты не спавнят субагентов» снято (глубина 3); в плагине можно поставлять Workflow-скрипты и `subagentStatusLine`.
4. **Подтверждённые P0 в базлайне:** `scripts/validate_state.py:39-57` ✓ не знает фазу `research_sufficiency_followup_pending` (валидатор отвергает корректный state; `test_phase_machine_coverage.py:58` ✓ маскирует); `python3` на типовой Windows — заглушка Microsoft Store → все 4 хука и 40+ вызовов молча не работают (03 §2); обязательная verbatim-цитата ≤30 слов у писателя (`agents/memo-writer.md:183,249` ✓) при бюджете ≤15 слов у исследователей (`agents/statutory-researcher.md:157` ✓) и опциональном raw-слое (`:164` ✓) — структурное давление к галлюцинации цитат; нет сквозного `source_id` (`agents/currency-checker.md:89,107` ✓ «identifier you assign», `agents/source-pack-builder.md:67` ✓ join «by slug or title»); failure-stub ревьюера пишет `overall_score: 0` (`scripts/validate_review_json.py:84` ✓) и обваливает среднее → ложный regression revert.
5. **Мёртвые фичи:** «пропорциональный follow-up» v1.1.0 — поле `reply_scope` читается в `phase-6.md:95` и `continue/SKILL.md:437` ✓ и не пишется нигде; `drafting_warnings[]` не имеет владельца в state и не читается писателем (01 C12–C13); docx без сносок вопреки `README.md:19,33` ✓ (03 §4).
6. **Реальность MCP не отражена в контрактах** (05 §5, эмпирика 9 живых вызовов): Legal Data Hunter Free — 10 запросов/мин, **20/день**, 600/30 дней; CourtListener — 5/мин, 50/час, **125/день**; код страны `GB` возвращает пустой список без ошибки (нужен `UK`); лаг индекса EUR-Lex ≈1 месяц; `resolve_reference` возвращает весь акт (GDPR = 358 КБ), не статью; eCFR/FederalRegister блокируют WebFetch; BAILII запрещает автоматический доступ.
7. **Ревью-луп опирается на шумный сигнал** (05 §2): 5 персон-ревьюеров, холистический `overall_score` без рубрики, плато при Δ<1.0 — внутри flip-rate LLM-судьи (≈13.6%); исследования показывают выигрыш от бинарных чеклистов с детерминированной агрегацией и почти нулевой прирост после 1–2 итераций.

- Полный переход оркестрации на Workflow tool. В v2.0 — только совместимость границ сегментов (§3.2) и пилот за флагом (§10).
- Interactive dashboard как обязательная функция (§7.5 — опционально, после пробы P3).

- «Accept as-is» после forced exit перед export; асинхронный source-review; `counterargument-reviewer` на Fable — на будущее (07 out-of-scope notes).

### 0.5. Инварианты v2 (M-слой; каждый — проверяемое утверждение)

- **M1 — Код держит инварианты, не память модели.** Переходы фаз, счётчики, бюджеты попыток, выбор списка агентов, эмиссия событий, атомарная запись state — только в `memoforge` CLI. Оркестратор-LLM не вычисляет ничего из этого.
- **M2 — Единственный писатель `state.json` — CLI** (`state_io.write` под файловым локом `state.lock`, tmp + `os.replace`, валидация по `schemas/state.schema.json` ДО замены). Ни агенты, ни хуки не пишут `state.json`; хуки только дописывают `events.jsonl`.
- **M3 — Оркестратор работает по протоколу `next → act → report`** (§3.1); `next` и `report` идемпотентны, а каждая изменяющая команда CLI принимает `--step` и фиксирует своё действие и закрытие шага одной транзакционной записью state, поэтому забытый или повторённый вызов не портит state и не повторяет побочный эффект; после суммаризации контекста работа восстанавливается одним `next`. (Протокол живёт в промпте ≈150 строк — риск вытеснения снижается размером, идемпотентностью и Stop-guard §8.3, но не исчезает.)
- **M4 — Все машиночитаемые артефакты — JSON по схеме; markdown-виды рендерятся скриптом** из JSON; ни один промпт не просит агента писать `.md`-вид параллельно с JSON.
- **M5 — Провенанс цитаты (ограниченная гарантия):** каждая blockquote в драфте имеет `quote_id`, который скрипт извлёк **точным совпадением** из raw-текста источника, сохранённого исследователем из ответа инструмента, с фиксацией `raw_sha256` в записи цитаты; каждая inline-ссылка — `[[src:<source_id>]]` из реестра; Sources-секцию генерирует рендерер. Цепочка хэшей начинается с файла, сохранённого агентом: платформа не даёт CLI идентификатора tool-вызова, поэтому соответствие «raw ↔ URL» подтверждается только `liveness` (сравнение sha тела ответа, где URL доступен) и помечается `confirmed|agent_saved`.
- **M6 — Freeze источников:** `sources pack --freeze` одной операцией под обоими локами публикует snapshot (`source-pack.json` + список `source_id` с версиями raw) и ставит `sources_frozen`; после этого регистрация возвращает ошибку; lint, аудит и рендер читают только snapshot.
- **M7 — Прогресс пишет рантайм:** `events.jsonl` заполняют хуки и CLI; агент делает максимум один Bash-вызов `mf agent log` на содержательный шаг; ни один агент не рендерит HTML.
- **M8 — Гейты пользователя — только на границах сегментов** и только через один парсер `gates.py` (для text-гейтов — `mf gate parse`, для AUQ-гейта — `mf report --answers`, который вызывает тот же парсер). После любого `Agent`-диспатча в сессии `AskUserQuestion` не используется, кроме гейта плана (фаза 4), который защищён text-fallback'ом (§2.4) до подтверждения пробой P4.
- **M9 — Always-deliver (для управляемых завершений при доступном writable `work_dir`):** терминальная фаза (`done|failed|cancelled_by_user`) записывается только после того, как `mf finalize` создал `deliverable.{docx|md}` и `summary.md`; `mf finalize --salvage` работает без `jsonschema` и на повреждённом `state.json` (собирает summary из имеющихся файлов). Прерывание сессии — не терминал, а resumable-состояние; Stop-guard §8.3 — дополнительная, не обязательная защита. Legacy v1-задачи — вне жизненного цикла v2 (`unsupported`, без finalize).
- **M10 — Детерминированное раньше LLM:** lint, аудит цитат, агрегация вердиктов, выбор итерации выполняются скриптом до/вместо LLM-ревью; LLM-ревьюеры видят lint-clean драфт либо драфт с приложенным `lint.json` после исчерпания раундов.
- **M11 — Один источник истины для перечислений:** фазы, режимы, события, лимиты, таблица деградаций определены в `scripts/memoforge/{phases,modes,events,limits,fallbacks}.py`; markdown-документы генерируются `mf docs render` и проверяются тестами.
- **M12 — Windows-first совместимость:** launcher discovery (`python`→`python3`→`py -3`), `utf-8-sig` чтение, `reconfigure(utf-8)` вывода, LF в репо, ни одного bash-only скрипта на критическом пути, хуки в трёх exec-form вариантах (`python`/`python3`/`py -3`) с дедупликацией событий.

```
                                          │   mf report --workdir W --step <id> [--agent <slot> --status ok|fail] …
                                          ▼
                     scripts/memoforge (пакет, детерминированная state machine)
                     ├─ phases/modes/limits/events/fallbacks (источники истины)
                     ├─ state_io (lock + atomic + schema)   ├─ dispatch (планы диспатча + промпты из шаблонов)
                     ├─ gates (парсер ответов)              ├─ sources/quotes/routing (реестр, провенанс, роутинг MCP)
                     ├─ lint / citations / review / revision
                     ├─ docx (AST-рендер, сноски, OSCOLA)   └─ finalize / tidy / analyze / probe
                                          │
          агенты (12, JSON-выходы по schemas/) ◄──── промпты диспатча рендерит CLI
          hooks: permission_gate · progress_logger (только events.jsonl) · stop_guard · ensure_deps(check)
          прогресс: description у Agent-вызова · 1 строка в чат · subagentStatusLine · (опц.) Artifact
```

Ключевое отличие от v1: **оркестратор не знает пайплайн.** Он знает протокол из трёх команд. Всё знание о фазах, параллелизме, промптах, событиях и переходах — в Python-пакете с тестами. Это снижает класс инцидентов «LLM забыл шаг» (01 §4.1) до одного правила протокола, восстановление после суммаризации — один вызов.

### 2.2. Схема `state.json` v2 (нормативно — `schemas/state.schema.json`; здесь — семантика)

Унаследованные поля: `task_id`, `user_query`, `created_at`, `language`, `work_dir`, `output_folder`, `mode`, `config`, `intake`, `classification`, `plan_approval`, `current_phase`, `dispatched_researchers`, `current_iteration`, `current_draft_path`, `iterations[]`, `client_readiness`, `final_status`, `final_docx_path`, `attempts`, `sufficiency_followup`, `remaining_blocking_issues`, `fallback_banners[]`.

Новые/изменённые:
- `schema_version: 2` (обязательно).
- `config.python_cmd`, `config.plugin_data_dir` (результаты discovery, §5.1), `config.source_review_gate: "auto"|"on"|"off"` (§2.3), `config.reviewer_list`, `config.max_iterations`, `config.lint_fix_rounds`, `config.intake_max_questions`, `config.mcp_budget {ldh, courtlistener, legalviz, uklegal, justicelibre, opencaselaw, fedregs, lex, casus, fas}` (совместимость: больше никем не читается, кроме сгенерированной таблицы режимов; квоты отслеживаются через `progress.mcp_calls` + `limits.MCP_QUOTA_SERVERS`/`MCP_PROVIDER_DAILY_LIMITS`), `config.writer_model`, `config.style_profile*` (как в v1).
- `drafting_warnings[]` — владелец: CLI (`sufficiency route`, `research` partial, гейт 8); читает `memo-writer` и рендерер (приложение).
- `sufficiency_followup {status, subset_u[], subset_r[], questions[], user_response, asked_at, answered_at}` — владелец CLI.
- `steps[]` — журнал шагов протокола: `{step_id, kind, phase, issued_at, attempt: n, reason: initial|failure|recovery|rerun, agents: [{slot, agent_type, attempt, status: null|ok|fail|no_change|superseded, reported_at, payload_ref, outputs: [{canonical_path, work_path, agent_sha256}]}], status: null|ok|fail|no_change|skipped|autoclosed, closed_at, result_ref}`. Execution identity = `(step_id, attempt)`; повтор шага увеличивает `attempt`: `reason: failure` расходует бюджет §2.2; `reason: recovery` (переиздание после прерывания) — не расходует; `reason: rerun` (то же действие с изменившимися входами: lint после fix, aggregate после повтора ревьюеров) — не расходует, а смысловые лимиты (`lint_fix`, `client_polish`) считают только диспатчи `reason: initial` своего вида. **Рабочее пространство попытки:** агент пишет только в `steps/<step_id>/a<attempt>/<slot>/<basename>` (путь подставлен в промпт; уникален по полной identity); потребители читают **только канонические** пути (`research/…`, `drafts/…`, `reviews/…`), которые создаёт исключительно `report`/autoclose при **публикации** принятого выхода; поздняя запись старой попытки остаётся в её каталоге и никого не трогает. **Авторитетный sha опубликованного файла** хранится в `published[]` (`{canonical_path, sha256, by: step|command, at}`) и обновляется в той же записи state каждой CLI-командой, законно преобразующей файл (`report`-публикация, `draft anchor`, pre-seed); `agent_sha256` в `steps[]` — история, а не предмет сверки. Команды, читающие канонический файл, сверяют его с `published[]`; несовпадение → `output_modified_after_publish` → шаг переиздаётся (`reason: recovery`). Marker `done` содержит `{task_id, step_id, attempt, slot, input_sha: {…}, output_sha: {…}}`; `report` и autoclose применяют один и тот же набор проверок §3.1.
- `final_status_reasons[]` — накопительный список причин `manual_review_required` (§2.1 стр.15).
- `draft_versions[]` — `{version, path, sha256, lint_clean: bool, citations_clean: bool, checked_at}`; `current_draft_sha` — sha версии, к которой относятся текущие вердикты (ревью/readiness/export привязываются к sha).
- `progress` — производное поле: `{phase, phase_started_at, route: [phases…], position: n, total: N, active: [{slot, agent_type, label, started_at}], last_line, artifact_url|null, mcp_calls: {server: n}}`; вычисляется CLI в `next`/`report` из `steps[]` и `events.jsonl` (никто больше его не пишет). `active[]` очищается при `report` шага и по TTL `limits.AGENT_STALE_SECONDS` (1800).
- `sources_frozen: bool` (M6); `cancel_requested: bool` (§2.4).
- `attempts` — таблица бюджетов (все — владелец CLI):

| Ключ | Единица учёта | Инкремент | Лимит | При исчерпании |
|---|---|---|---|---|
| `plan_edit` | задача | ответ `edit` на гейте 4 | 5 | forced approve **последней поданной версии плана** (после применения последней правки) + баннер |
| `sufficiency_user_followup` / `sufficiency_research_followup` | задача | вопрос пользователю (гейт 7) / повторный researcher-проход | 2 / brief 1, full 2 (D-116) | гэпы → `drafting_warnings` |
| `research_dispatch_retry` | фаза `research` (сбрасывается при повторном входе в фазу из 6/7) | повторный dispatch незакрытых слотов | 1 | продолжить с валидными слоями или `research_insufficient_pending` |
| `currency_regate` | задача | возврат 9→6 | 1 | продолжить в `source_pack` |
| `lint_fix{draft_version}` | версия драфта (v1, v2, polish) | dispatch writer-fix | `config.lint_fix_rounds` (polish: 1) | в `revision_loop`/`export` с lint.json + баннер |
| `reviewer_json_retry{iteration,kind}` | итерация×ревьюер | невалидный JSON | 1 | stub |
| `reviewer_rerun{iteration}` | итерация | повтор упавших ревьюеров | 1 | `manual_review_required` (§4.5) |
| `client_polish` | задача | dispatch polish | `config.max_client_polish` | `manual_review_required` |
| `single_dispatch_retry{step_id}` | шаг вида dispatch(1): analyst, sufficiency, currency, writer v1/vN, **writer fix, writer polish**, client-readiness, mediator | `fail`/невалидный выход (`reason: failure`) | 1 | по таблице §2.1 (писатель → `failed`; fix/polish → продолжить с текущей версией + баннер; остальные — деградация по §2.1) |
| `inline_llm_retry{step_id}` | шаг inline-llm | невалидный результат | 2 | `failed` |
| `gate_parse_errors{gate}` | гейт | нераспознанный ответ | 3 | intake/followup → дефолты с `assumptions_accepted=false`; plan(text-fallback) → `cancel`; source_review → continue; insufficient → cancel |

Правила: каждый повтор с `reason: failure` относится ровно к одному бюджету выше (никакого общего `step_retry`); переиздание `reason: recovery` (прерывание между `next` и `report`) бюджет не расходует; `reviewer_json_retry{iteration,kind}` считается по итерации и **не сбрасывается** после `reviewer_rerun`; смысловые лимиты `lint_fix`/`client_polish` считают диспатчи, а провал такого диспатча — `single_dispatch_retry`. **Единая политика script-ошибок:** ошибка CLI на `script`-шаге → оркестратор повторяет команду один раз (`reason: recovery`), затем `mf finalize --reason cli_error`. Тесты бюджетов утверждают **число реальных диспатчей** при повторных `next`/`report`, а не значение счётчика.

Удалены: `live_progress`, `config.visualize_*`, `config.live_progress_enabled`, `rel_work_dir` (кликабельность дают карточки `Write`/`Read`; в чате печатается абсолютный путь), `max_intake_iterations`, `*_gate_choice`, `heartbeat_choice`, `exit_threshold_score`, `events_path` (файл всегда `<work_dir>/events.jsonl`).

**Запись (M2):** `state_io.write(mutator)`: взаимное исключение — **системный advisory-лок на постоянно существующем файле `state.lock`** через один общий helper `state_io.FileLock` (`fcntl.flock(LOCK_EX)` на POSIX; на Windows `msvcrt.locking(LK_NBLCK, 1)` **после `seek(0)` — всегда один и тот же первый байт файла**, т.к. API блокирует диапазон от текущей позиции; ожидание с таймаутом `limits.LOCK_TIMEOUT=30` с через повтор неблокирующей попытки). Lock-файлы создаются при `task new`, никогда не удаляются и не заменяются (`tidy` и `finalize` их не трогают). Лок освобождается ОС при смерти процесса — никаких TTL, PID-проверок и reclamation не требуется. Под локом: read → mutate → сериализация → валидация по схеме → `NamedTemporaryFile(dir=work_dir, prefix=".state-", delete=False)` → `os.replace` (ретрай ×5 на `WinError 32`) → unlock. Невалидный результат — исключение, файл не меняется. Мутация и закрытие шага (`steps[]`) — в одном `write`. **Порядок вложенности локов — строго `state.lock` → `sources.lock` → `events.lock`**; захват «вверх» (например, `state` под `events`) запрещён и проверяется helper'ом (исключение `lock_order_violation`). Тесты: два процесса, один убит под локом — второй получает лок; взаимное исключение на Windows (два процесса, счётчик).

**Файловые побочные эффекты команд (замена «транзакциям»):** каждая `--step`-команда, создающая или преобразующая файлы (`sources pack --freeze`, `draft anchor`, pre-seed драфта в `revision next`, `render`, `docx render`, `finalize`), сначала копирует свои **входы** и пишет **результат** в рабочий каталог шага `steps/<step>/a<n>/cli/`, затем публикует канонический файл через tmp + `os.replace` и закрывает шаг в state (`published[]` с новым sha) одной записью. Все такие команды **детерминированны по входам**, поэтому окно «канонический файл уже заменён, state ещё не записан» восстанавливается так: при повторе незакрытого шага команда берёт вход из рабочего каталога, пересчитывает результат и, если канонический файл равен пересчитанному — просто закрывает шаг (никакой произвольный sha авторитетным не признаётся); иначе публикует пересчитанный результат заново. Сверка потребителей с `published[]` выполняется **после** такого replay (порядок в `next`: сначала закрыть/переиграть незакрытые script-шаги, потом выдавать следующий). Для freeze авторитетен файл snapshot. Тесты `test_crash_between_file_publish_and_state_close` для каждой такой команды, включая `anchor replace → crash → resume → lint`.

### 2.5. Re-entry и объединение `memo`/`continue`

Оба скилла вызывают один router (`skills/memo/references/router.md`, ≈60 строк). `/memoforge:memo "<q>"` → `mf task new --query "<q>"` → loop. `/memoforge:continue [task_id] [reply…]` → `mf task resolve [task_id]` (последняя незавершённая) → если `reply` непустой и фаза — гейт: `mf gate parse` → loop. Бесслэшевый ответ на гейт в той же сессии обрабатывает тот же router; подсказка гейта содержит слэш-команду первой строкой.

**`task new` (`task.py`):** slug санитизируется (`[a-z0-9-]`, ≤40), `work_dir` резолвится по цепочке `userConfig.output_folder` → `$MEMOFORGE_OUTPUT_FOLDER` → `<$CLAUDE_PROJECT_DIR|cwd>/memoforge` (source `project_folder` — рабочая папка сессии; пропускается, если это plugin root — `pylauncher.plugin_root()`, `$CLAUDE_PLUGIN_ROOT` или любой каталог с `.claude-plugin/plugin.json` — сам домашний каталог или корень ФС) → `Path.home()/Documents/memoforge` (не `$HOME`) → `<cwd>/outputs/memoforge-work`; первый writable; результат и причина — в событии `work_dir_resolved`. **`plugin_data_dir` — единая цепочка для `mf`-обёрток и пакета:** `${CLAUDE_PLUGIN_DATA}` → `%LOCALAPPDATA%/claude/plugin-data/memoforge` (Windows) / `~/.claude/plugin-data/memoforge` → `<plugin_root>/.data` (последний fallback не зависит от задачи). **Опции `userConfig` резолвятся цепочкой** явный флаг (`--option key=value`) → `CLAUDE_PLUGIN_OPTION_*` → `<plugin_data_dir>/options.json` (зеркало, которое SessionStart-хук пишет из env, а `mf config set` — вручную) → default манифеста; значение с неразвёрнутым `${…}` игнорируется, а источник каждого ключа возвращается в ответе `task new` (`options_source`). **Публикация результата (D-109):** после `deliverable` и `summary.md` `mf finalize` копирует их вместе с `sources/` (source-pack плюс сырой текст каждого `critical`/`supporting` источника) в `<publish_folder>/memoforge/<slug>/`; корень — опция `publish_folder`, иначе `/mnt/user-data/outputs`, если он есть и доступен на запись, иначе не копируется ничего; сбой копирования — баннер `publish_failed`, а не ошибка прогона. Тесты: пустой `$HOME`, slug с пробелами/`..`. **`finalize` публикует папку и копию `memo-<slug>.<ext>` в корень outputs; роутер показывает её через `present_files` (D-167)**.

## §3. Протокол оркестратора `next → act → report`

### 3.1. Команды

`mf next --workdir W` → JSON одного из видов (`command[]` всегда содержит абсолютный путь к `scripts/mf` (`mf.cmd` на Windows), подставленный CLI):

```jsonc
{"step_id":"s-017","kind":"dispatch","parallel":true,"phase":"research",
 "agents":[{"slot":"statutes","subagent_type":"memoforge:legal-researcher","model":"sonnet","description":"P5/13 · legal-researcher · statutes",
            "prompt":"<полный текст из prompts/legal-researcher.md с путями, ${step_id}, ${attempt}, ${slot}>",
            "expected_outputs":[{"canonical":"research/statutes.json","work_path":"steps/s-017/a1/statutes/statutes.json","schema":"research-findings"}]}, …],
 "attempt":1,"reason":"initial","chat_line":"Phase 5/13 — research: 3 researchers dispatched (statutes, case_law, doctrine)"}
{"step_id":"s-018","kind":"script","attempt":1,"phase":"drafting","command":["<abs>/scripts/mf","draft","lint","--workdir","W","--step","s-018","--attempt","1","--draft","drafts/v1.md"],"chat_line":"…"}
{"step_id":"s-004","kind":"gate-auq","attempt":1,"generation":0,"phase":"plan_approval_pending","questions":[…AskUserQuestion-schema…],"text":"<plan digest>","text_fallback":"<подсказка>"}
{"step_id":"s-002","kind":"gate-text","attempt":1,"generation":0,"phase":"intake_questions_pending","text":"<готовая подсказка>","end_turn":true}
{"step_id":"s-011","kind":"inline-llm","attempt":1,"phase":"planning","instruction":"<что сгенерировать>","write_to":"steps/s-011/a1/orchestrator/plan.json","schema":"schemas/plan.schema.json"}
{"step_id":"s-099","kind":"terminal","phase":"done","text":"<итог с путями>"}
```

`mf report --workdir W --step <id> --attempt <n> [--agent <slot>] --status ok|fail|no_answer [--answers <json> --generation <g>] [--stdout <file>]` — для `dispatch`, `inline-llm` и `gate-auq`. **Порядок проверок:** (0) identity `(step, attempt)` не совпадает с текущей → `identity_mismatch` (ошибка, ничего не меняется); для гейта `generation` ≠ текущему → `stale_generation` (ответ отклонён); (1) шаг/слот уже закрыт → no-op `{accepted:true, already_reported:true}`; (2) содержательная проверка:
- для `dispatch` — по одному вызову на слот (или один вызов без `--agent` = все слоты ok); шаг закрывается, когда отчитались все слоты. CLI проверяет **completion** слота: marker `steps/<step_id>/a<attempt>/<slot>/done.json` (пишет агент последним действием `mf agent log --state done` — **обязательная** часть контракта, в отличие от best-effort `--state step`; `agent log` сам вычисляет `input_sha` по списку входов из промпта и `output_sha` по файлам рабочего каталога), совпадение `input_sha` marker'а с sha входов, зафиксированных CLI при выдаче попытки (`steps[].inputs`), существование и валидность по схеме файлов в рабочем каталоге попытки, совпадение их sha с `output_sha` marker'а; для писателя — сравнение с seed: sha == seed → `no_change` (v1: `fail`; fix/polish: закрыть шаг `no_change`, продолжить с прежней версией; vN-ревизия: `fail` с бюджетом `single_dispatch_retry`, после исчерпания — `revision next` считает блокеры неустранёнными). Затем **публикует** файлы в канонические пути (tmp+replace), обновляет `published[]`, копирует `--stdout` в `steps/<step_id>/a<attempt>/<slot>/stdout.txt`, пишет `agent_returned`, обновляет state;
- для `inline-llm` — `report --status ok` после записи файла оркестратором в `steps/<step>/a<n>/orchestrator/<basename>`; CLI валидирует по схеме, публикует и закрывает шаг;
- ответ `{accepted: true, next_hint}` | `{accepted:false, errors:[…], retry:{step_id, attempt, agents:[slots]}}`.

`script`- и `gate-text`-шаги **не требуют `report`**: каждая изменяющая команда (`sufficiency route`, `sources pack --freeze`, `draft finish` (= anchor|lint|audit-citations), `review aggregate`, `revision next`, `gate parse`, `docx render|validate`, `finalize`) принимает `--step <id> --attempt <n>`, выполняет действие и закрывает шаг одной записью state; повторный вызов с той же identity — no-op с прежним результатом (`steps[].result_ref`); та же identity с другими аргументами — `identity_mismatch`. Повтор операции с новыми входами (lint после fix, aggregate после повтора ревьюеров) `next` выдаёт как тот же `step_id` с `attempt+1`, `reason: rerun`. Незакрытый `script`-шаг `next` возвращает повторно (`reissued`), не продвигая фазу. `draft anchor` и pre-seed (`revision next`) обновляют `published[]` в своей записи state — последующий lint сверяет файл с новым авторитетным sha (сценарий `report v1 → anchor → lint` проходит без ложного recovery). Pre-seed для vN создаётся CLI **в рабочем каталоге попытки писателя** (`steps/<step>/a1/writer/v<N+1>.md`) и одновременно публикуется как `drafts/v<N+1>.md` (seed); писатель правит рабочую копию, `report` сравнивает с seed и публикует. Оркестратор после `script`-шага просто вызывает `next`.

Исходы шага (`machine.py`):

| kind | `fail` или невалидный выход | бюджет (§2.2) | после исчерпания |
|---|---|---|---|
| dispatch (N слотов) | повтор только незакрытых слотов с новым `attempt` и текстом ошибок в промпте | `research_dispatch_retry` / `reviewer_json_retry` / `reviewer_rerun` / `single_dispatch_retry` | по таблице §2.1 |
| script | ошибка CLI — не бизнес-исход; повтор оркестратором один раз, затем `finalize(failed)` | — | `failed` |
| inline-llm | повтор с ошибками схемы | `inline_llm_retry` 2 | `failed` |
| gate-* | `gate_parse_errors` | 3 | §2.2 |

Правила: (1) оркестратор НИКОГДА не выполняет шаг, не полученный от `next`; (2) `dispatch parallel:true` — все `Agent`-вызовы в ОДНОМ сообщении (единственное правило параллелизма в промпте; `events analyze` детектирует серийность); (3) `next` без закрытия предыдущего dispatch-шага: слоты, у которых есть marker текущего `attempt` и валидные attempt-специфичные выходы, закрываются автоматически с публикацией (событие `step_autoclosed`); остальные слоты переиздаются с `attempt+1`, `reason: recovery` (старая попытка помечена `superseded`, её поздние файлы `.a<n>` игнорируются); пустой `expected_outputs` никогда не даёт autoclose; каждый вызов `next`/`report` пишет событие `cli_call` (для G2); (4) `description` формируется CLI по шаблону `P<n>/<N> · <agent> · <label>`, где `N` = число нетерминальных фаз, достижимых при текущем `config` (пересчитывается в `next`); (5) `sources register` идемпотентен по `(layer, url|citation_form)`; (6) `next` пишет событие `step_issued` (гарантированный след старта, независимо от хуков и агентов).

### 3.2. Сегменты и границы (совместимость с Workflow)

Сегмент = фактический маршрут от текущей точки до следующего гейта или терминала; фиксированного набора фаз сегмент не обещает. Типовые сегменты: S1 (фаза 1), S2 (фаза 3), S3a (5→6, возможно с возвратом 6→5), S3b (9→10; при regate 9→6 сегмент завершается и router продолжает по маршруту S3a), S4 (12→15). Внутри сегмента `next` не возвращает `gate-*`. Workflow-пилот (§10) представляет только S3a и S4 как скрипты; S3b — нет.

### 3.3. Промпты диспатча

`scripts/memoforge/prompts/<agent>.md` — стандартный `string.Template` с плоскими именами `${work_dir}`, `${paths_agent_core}`, `${paths_checklist}`, `${paths_template}`, `${prose_style_path}`, `${layer}`, `${layer_rules}` (**только строка своего layer** из таблицы §4.3), `${iteration}`, `${step_id}`, `${attempt}`, `${slot}`, `${mf}` (абсолютный путь к `mf`/`mf.cmd`); рендер через `substitute()` (не `safe_substitute`) — нераскрытый плейсхолдер = исключение. Каждый промпт начинается с первого действия агента `${mf} agent log --workdir … --step ${step_id} --attempt ${attempt} --slot ${slot} --state start` и заканчивается последним `… --state done` (пишет completion marker, §3.1). `test_prompts.py` сравнивает рендер каждого шаблона для Brief и Full с golden-файлами и проверяет абсолютность путей.

### 3.4. Router `skills/memo/SKILL.md` (≈150 строк)

Frontmatter: `name: memo`, `disable-model-invocation: true`, `argument-hint`, `allowed-tools: Read, Write, Bash, Agent, AskUserQuestion, WebFetch, WebSearch, mcp__*` (роль allowed-tools — снятие промптов на turn; MCP-инструменты главной сессии наследуются агентами). Содержание: authority hierarchy (6 строк); untrusted-content (3 строки); протокол §3.1 с примером каждого `kind`; правило «параллельный dispatch = одно сообщение»; печать `chat_line`; поведение при `accepted:false`; при ошибке CLI на `script`-шаге — повторить команду один раз, при повторной ошибке `mf finalize --reason cli_error` и END (та же политика, что §2.2). Никаких фазовых процедур.

- **Таблица правил по layer** (в промпт попадает только своя строка):

| layer | WebSearch как первичный инструмент | Что можно цитировать |
|---|---|---|
| statutes | нет (discovery only) | MCP-документы; WebFetch issuing-body порталов |
| case_law | нет | MCP-документы; официальные суды/Find Case Law/CourtListener |
| doctrine | **да** (как `agents/doctrinal-researcher.md:81` ✓) | + официальные регуляторные руководства, рецензируемые публикации, SSRN-класса репозитории (критерии `:87-91` ✓) |

- **Текст источника сохраняет код (D-205).** Каждый `critical`/`supporting` источник до первой находки либо сохраняется, либо регистрируется. Веб-источник — только `mf sources save --layer L --title … --citation … --tier T (--url <адрес документа> | --resolve vsrf|sudact) [--expect-article N | --expect-number … --expect-date YYYY-MM-DD] [--meta …]` (D-199): код скачивает, удостоверяет (D-203) и регистрирует; реквизиты передаются всегда, номер — как напечатан, со скобочным суффиксом (`305-ЭС24-8702 (1,3)`; суффикс резолвер сам снимает для поиска), дата — собственная дата акта, а не дата выдачи портала. `mf sources register --raw-file <файл>` остаётся ровно для трёх случаев: ответ MCP-инструмента целиком (`--raw-kind excerpt`), файл клиента (`--raw-kind client_file`) и хост вне allowlist после отказа `save` с `host_not_allowed` (`--raw-kind agent_summary`); `register` после отказа `save` несёт отказ в `--meta` (`"save_outcome": "refused:<код>"`), чтобы рецензент достаточности не требовал повторить попытку; иного `save_outcome` `register` не принимает (`save_outcome_not_allowed`): `full_text` и `excerpt:*` пишет только код. Выдержку или конспект поднимает до полного текста `save` поверх той же записи (та же `--citation` или тот же `--url`). Адрес, который вернул MCP-инструмент, — эндпоинт и `--url` не бывает. `background` — без текста. **Ответ `save` → следующий ход** (промпт исследователя): `full_text` — цитировать; `excerpt:<причина>` — цитировать как выдержку, тот же адрес не повторять; `requisites_mismatch` — перепроверить номер и дату, канал не менять (если резолвер уже удостоверил адрес, а повторная загрузка дала другое, — как `channel_unavailable`); `requisites_ambiguous` — выбрать один из `candidates` самому и сохранить его `--url`; `channel_unavailable: <причина>` / `channel_budget_spent` — запасные пути (LDH `RU/Sudact`, веб-поиск) → `save --url` с теми же `--expect-*`; `channel_unavailable: captcha` — то же, и канал до конца прогона не трогать, страницу не обходить, пользователя решать капчу не просить — без исключений; sudact.ru после капчи закрыт и для `save --url`, поэтому адреса sudact.ru от LDH и веб-поиска в `save` не передаются: ответ LDH регистрируется как `excerpt`, копия акта на другом разрешённом хосте сохраняется `save --url`; после `channel_budget_spent` — так же: бюджет — хоста, и каждый запрос к sudact.ru, `save --url` включительно, считается в нём (финальное ревью, C); сохранение `--method POST` несёт `--public-url` — публичную страницу документа (для статьи Normattiva — `https://www.normattiva.it/uri-res/N2Ls?` и URN тела), без неё отказ (финальное ревью, A); `host_not_allowed` — единственный случай `register --raw-kind agent_summary`. Рецензент достаточности читает `raw_kind`: `critical` не `full_text`/`client_file` — `missing`-пробел со средством `mf sources save`, только если в записи нет `meta.save_outcome`; запись с `refused:*`/`excerpt:*` на второй круг не отправляется; запись с `raw_original_path` не считается «без текста» — это источник, чьи реквизиты и цитаты код не проверял.
- **Роутинг источников — `routing.py` = статическая таблица предпочтений (без новых HTTP-клиентов):** для каждой пары `layer × jurisdiction` — порядок инструментов и предпочтительные домены WebFetch. Коды стран нормализует CLI (`GB`→`UK`). Дневные потолки `legalviz` и `uklegal` — в `limits.py`, отсутствие любого из namespace попадает в вопрос `Sources` гейта плана (D-105). **Франция идёт через JusticeLibre** (`justicelibre`, `https://justicelibre.org/mcp`, пятый bundled-сервер; свободный, без ключа): статуты — `justicelibre_get_law_article` (контракт `code` = короткая аббревиатура кодекса, `num` = номер статьи; при неверном коде сервер сам отдаёт все 79 поддерживаемых) и `justicelibre_resolve_law_number` для актов вне кодексов, резерв — `ldh_resolve_reference` по `FR/LegifranceCodes` (229 364 статьи; `ldh_search` по ней — шум, LDH резолвит точную цитату и не является поисковиком); практика — `justicelibre_search_judiciaire`/`get_decision_judiciaire`, `search_conseil_etat`/`get_ce_decision`, `search_cc` (`courdecassation.fr/decision/<id>` — 255-байтовый JS-каркас, не `--url`); доктрина — `justicelibre_search_cnil`, `search_doctrine`; для EU case_law `justicelibre_search_cjue`/`get_decision_cjue` — альтернативный источник текста после LegalViz. Регистрируется `source_url` на Légifrance; сам портал закрыт managed challenge Cloudflare, бесключевой резерв с текстом — `code.travail.gouv.fr`. **Швейцария идёт через OpenCaseLaw** (`opencaselaw`, `https://mcp.opencaselaw.ch/mcp`, шестой bundled-сервер; свободный, без ключа, данные CC0): `opencaselaw_get_law(sr_number, article)` плюс `search_laws`, `get_article_history` — статуты с `source_url` на `fedlex.admin.ch` и перечнем уже назначенных консолидаций (он же ответ на вопрос актуальности); `opencaselaw_search_decisions`/`get_decision`/`get_regeste`/`find_leading_cases` — практика (`bger.ch`); `opencaselaw_get_doctrine`/`search_commentaries` — доктрина; `entscheidsuche` не бандлится. `CH` живёт в `routing.EXTRA_JURISDICTION_ROWS` и подмешивается `route()`, список `MEMBER_STATES` остаётся EU-only. Дневные потолки `justicelibre` и `opencaselaw` — 60, как у LegalViz/UK Legal (D-148). US statutes → govinfo (U.S. Code); US regulations → fedregs_regulations_get_cfr_section / _browse_cfr (eCFR) и fedregs_regulations_search_rules / _get_document (Federal Register), fallback — открытые API через mf sources fetch (D-160, D-162). UK statutes → uklegal_*, затем lex_* (explanatory notes, amendments; D-161). **Россия** (`RU`, D-184..D-186): практика высших судов через **CasusLegal** (`casus`, `https://mcp.casus.legal/one/mcp`, платный аккаунт; `casus_casuslegal_search_practice`/`find_term`/`get_case_details`, корпуса `sip_*`/`kas_*`), практика ФАС по рекламе через **fas-search** (`fas`, `https://search.delay-rag.ru/mcp/`, бесплатно, 300/сутки на IP — ориентир, не квота), Casus и FAS дают реквизиты, текст судебного акта сохраняет код (D-205): акт судебной коллегии ВС — `save --resolve vsrf`, акт арбитражного суда или суда общей юрисдикции — `save --resolve sudact`, постановление Пленума или Президиума — `save --url` с опубликованной страницы (`base.garant.ru`, `garant.ru`); запасные пути — LDH `RU/Sudact` и веб-поиск → `save --url`; решение ФАС судебным актом не является — ответ `fas_get_case_details` регистрируется как `excerpt`; законодательство — LDH `RU/PravoGovRu` (официальные тексты, поиск акта и редакции на дату), источник — одна статья, которую код сохраняет со страницы статьи `www.consultant.ru` (`save --url … --expect-article N`, строка редакции — в `--meta` как `edition`), вторая копия — `base.garant.ru` (`pravo.gov.ru` через WebFetch не отвечает, `kad.arbitr.ru` за капчей — не источники); доктрина — WebSearch, `zakon.ru`, `cyberleninka.ru`. `RU` живёт в `EXTRA_JURISDICTION_ROWS` рядом с `CH`; preflight проверяет три веб-хоста. - **Учёт MCP-вызовов (квоты + телеметрия; остаток провайдера CLI не знает):** `PostToolUse`-хук пишет `mcp_call {server, tool, ok|error}` по всем namespace из `intake/mcp-probe.json` (matcher `^mcp__` с фильтром по алиасам серверов в самом хуке (D-134), а для иных namespace в Cowork счётчик ведёт сам агент через `mf agent log --mcp <server>`, best-effort); CLI агрегирует `progress.mcp_calls` (успешные и ошибочные отдельно); квотируемые серверы (`limits.MCP_QUOTA_SERVERS`: LDH 10/день, CourtListener 125/день) сравниваются с `limits.MCP_PROVIDER_DAILY_LIMITS`, остальные — мягкий потолок `limits.MCP_SOFT_CAP_PER_RUN` (100 вызовов на прогон) с баннером `mcp_soft_cap_exceeded` в терминальной записи и разделом «MCP calls» в `summary.md`; оценка потребности считается при формировании гейта плана для обоих режимов (`layers×issues×2` + доля intake/currency) и сравнивается только с дневными квотами квотируемых серверов **как с верхней границей** (реальный остаток неизвестен — текст вопроса `Sources` так и говорит); в промпт исследователя подставляется уже сделанное `${mcp_spent}`; ожидание `Retry-After` ограничено `limits.RETRY_AFTER_CAP=60` с — дневной throttle не подвешивает прогон, а переводит в fail-soft. `config.mcp_budget` оставлен в state/config для совместимости и больше никем не читается.
- **Слова суда и самопроверка цитат (D-209).** Находка о том, что суд установил или применил, стоит на собственном высказывании суда: пункт договора, позиция стороны или взгляд нижестоящего суда, которые акт воспроизводит, описываются как таковые («суд воспроизвёл условие оферты …», «истец полагал …»), `quote_short` позиции суда — из слов самого суда; вывод, которого текст не несёт, не пишется от имени суда. Находки об одном источнике по разным issues читаются вместе и друг другу не противоречат. Акт вышестоящего суда, который собственный `proposition` находки называет основанием мотивировки суда, сохраняется (`mf sources save`: `--resolve vsrf` для акта коллегии ВС, `--url` для обзора практики и постановления Пленума) или вносится в `considered_excluded` с причиной; акты, которые решение цитирует, но ни одна находка не называет, не трогаются. До `--state done` исследователь прогоняет `mf quote locate --workdir W --source <source_id> --text "<quote_short>"` для `quote_short` каждой `critical`-находки; при `not_found`/`ambiguous` цитата заменяется точным непрерывным отрезком из ответа (≤15 слов) либо опустошается с понижением `confidence`; один lookup на находку плюс один повтор заменённой цитаты. Рецензент достаточности требует у каждого права, обязанности или средства защиты из вопросов плана находку с нормой, которая его устанавливает (иначе `missing`-пробел для `statutes`), и может выборочно проверить до 5 `critical`-находок практики через `mf quote locate`: позиция, найденная только в воспроизведённом актом условии, а не в мотивировке суда, — пробел для `case_law`. **Модель слоя:** `dispatch.RESEARCH_LAYER_MODELS = {"case_law": "opus"}`; `researcher_specs` передаёт слоту `model=`, поэтому первый проход, дозапрос и повтор слота `case_law` идут на `opus`, а `statutes` и `doctrine` — на `sonnet` по строке агента (§4.1; frontmatter и `lib/models.md` не меняют модель, «Why» называет переопределение). Промпт-шаблон несёт команду и формулировки, файл агента — по строке на правило.
- Выход: `research/<layer>.json` (`research-findings.schema.json`): по каждому `issue_id` — `findings[] {source_id, proposition, pinpoint, role: rule|application|risk|background|contrary, weight: binding|persuasive|non_binding, confidence: high|medium|low, tier, quote_short ≤15 слов, contrary_point?}` — смысловые поля source-pack базлайна (`agents/source-pack-builder.md:40,44-48,59-63`) сохраняются на уровне «источник × вопрос»; `mf sources pack` переносит их без вывода веса из tier (один источник может иметь разные роли по разным issues). Md-вид рендерит `mf render research`. Промпт ≤120 строк.

### 4.4. `memo-writer`

- Вход v1: `plan.json`, шаблон, `intake/*`, `research/*.md` (рендер), `research/source-pack.json`, `research/currency.json`, `state.drafting_warnings`, профиль стиля/`lib/prose-style.md` (сокращённый). Не читает raw и reviews.
- Цитирование: `[[src:<source_id> <pinpoint>]]`; цитата необязательна — blockquote (`> [[q:<quote_id>]] <текст>` с `quote_id` от `mf quote extract`) ставится только там, где важны точные слова, а иначе норма излагается своими словами с `[[src:]]`; любая цитата проверяема (C-02). `quote_id` однозначно определяет `source_id`: сноска и все C-проверки применяются к источнику цитаты и без соседнего `[[src:]]`. Sources-секцию писатель не пишет.
- vN: pre-seeded копия (делает `mf revision next`), `Edit` только секций из `mediator.json[].section_id`; якоря `<!-- §s-4-1 -->` ставит `mf draft finish` (`draft anchor` внутри него) после v1.
- Fix-цикл после lint: writer получает `lint.json`/`citations.json` и правит только указанные позиции.
- Промпт ≤150 строк, обычный тон. Шаблон `classical-memo`: conclusion-first, Rule explanation, **обязательное предложение с контраргументом и его разрешением** внутри Analysis (CREAC/CRRACC; проверяет чеклист `counterargument-reviewer`); четырёхбитная структура сохраняется.

### 4.5. Ревью-луп (Full ≤2 итерации; Brief 1)

1. `mf draft lint` → fix-цикл (≤`lint_fix_rounds`) → `mf draft audit-citations` → fix (те же раунды). Не сошлось → в луп с `lint.json`+`citations.json` как входом ревьюеров + баннер.
2. Диспатч ревьюеров одним сообщением. Каждый — изолированный грейдер по **бинарному чеклисту** `lib/checklists/<kind>.json` (`{id, text, tier: substance|form, hard_fail}`; источники — Columbia/Georgetown/UNH memo checklists, CRRACC, house-style); порядок пунктов перемешивается детерминированно по `task_id`. Выход `reviews/v<N>-<kind>.json` (`review.schema.json`, `oneOf` по `reviewer` + отдельный вариант `status: failed` для stub): `reasoning` (первым), `draft_sha`, `checklist[] {id, pass: true|false|unknown, evidence}`, `issues[] {severity: blocker|major|minor, category, section_id, issue, suggestion, checklist_id?, lens|issue_category|attack_vector, source_evidence? (citations/counterarguments)}`, `text_checks[]?` (citations/counterarguments), `verdict ∈ {approved, needs_revision}`. Валидатор (`review validate`): набор `checklist[].id` **в точности** равен набору из файла чеклиста (без дублей и неизвестных); каждый `pass=false` у `hard_fail`-пункта имеет issue с `severity=blocker` и `checklist_id`; `unknown` у `hard_fail`-пункта несовместим с `approved` (валидатор понижает вердикт до `needs_revision` и добавляет issue `unverified_hard_fail`); `approved ⇔ 0 blockers`; `draft_sha` == текущий. Кап «≤5 major» — рекомендация в промпте, не `maxItems`. Промпт явно: «`approved` — нормальный исход». Ревьюеры не видят `changelog.md`, прошлых оценок, пометок «final». Писатель не видит сырые ревью.
   **Сверка с сохранённым текстом (D-208).** Finding — ключ сопоставления: что записал исследователь; для `critical`-источника сохранённый текст — потолок, при расхождении побеждает текст. `citations` (бюджет `${lookup_budget}` = 20) и `counterarguments` (8; у logic/form и прочих агентов — 0) проверяют утверждения командой `mf quote locate` (lookup — 1, статья целиком — 1, судебный акт целиком — 3) в порядке: утверждения, которые рецензент собирается пометить или переписать (обязательно до такого issue); что суд установил или применил — для `critical`-практики, несущей вывод; норма закона под пунктом резюме, выводом или строкой риска; остальное, пока есть бюджет. В первый пункт порядка `citations` входит и каждый кандидат в CIT-01 — утверждение о праве, чья парная находка не записывает норму черновика (находки нет или она о другом): до остальных пунктов читается целиком цитируемая статья или ищутся слова самого суда. `counterarguments` проверяет источник до того, как предложение утверждает, что в нём сказано. Позиция суда — то, что говорит сам суд, а не пересказанный актом пункт договора или позиция стороны. Что суд сделал (установил, применил, последовал, взял за меру), подтверждает только собственное предложение суда; пересказанный пункт оферты подтверждает лишь сказанное об оферте и приписывается оферте; без такого предложения — только снять атрибуцию или оговорить её как нерешённую. `source_evidence.passage` — точный непрерывный фрагмент сохранённого текста, без многоточий и склеек. На каждую проверку — строка `text_checks {source_id, section_id, status: confirmed|contradicted|inconclusive|not_reached, finding_disagrees, note}`: `contradicted` — блокер на предложение черновика, `unsupported_claim`, CIT-01 (нормы нет) или CIT-02 (позиция искажена), с `source_evidence {source_id, status: confirmed|contradicted, passage ≤600}`; `inconclusive` и `not_reached` — не issue, CIT-02 оценивается по finding'у. Отсутствие и противоречие выводятся только из чтения целиком (статья; акт через Read по `raw_path`) или из найденного фрагмента собственной мотивировки суда; ответы `not_found` ничего не доказывают. Блокер вешается на предложение черновика, не на finding: черновик, согласный с текстом, проходит (`finding_disagrees: true`). Предложение, говорящее писателю, что содержит источник, несёт `source_evidence.status: confirmed` с фрагментом, иначе только снять, оговорить или пометить нерешённым. Норма на источнике, где её нет, — CIT-01 `unsupported_claim` даже при токене; CIT-04 — только неверный пинпоинт. Для неанглийского мемо `citations` пишет `issue_client` и для `major`.
3. `mf review aggregate --iteration N --step`: валидация (ретрай ×1; stub = `status: failed`, без чеклиста и вердикта), **включение детерминированных блокеров**: актуальные `lint.json`/`citations.json` для `draft_sha` добавляются в набор блокеров как источник `deterministic` (LLM-вердикт их не снимает), дедупликация issues только внутри одной категории (`section_id` + категория + Jaccard ≥0.8; сохраняются provenance всех ревьюеров и максимальная severity; issues с противоположными выводами по одному `section_id` не сливаются, а помечаются `conflict`), подсчёт `substance_blockers` (logic/citations/counterarguments/deterministic), `form_blockers`, `failed_reviewers[]`, `coverage` (набор успешных ревьюеров), `pass_ratio` (информационно), запись `iterations[N]`.
4. `mf revision next --step` (единственный владелец `current_iteration`) — **первая совпавшая ветка**:
   1. `failed_reviewers ≠ ∅ ∧ attempts.reviewer_rerun[N] < 1` → повторный dispatch только упавших (`attempt+1`), `reviewer_rerun[N]++`, возврат к п.3;
   2. `failed_reviewers ≠ ∅` (бюджет исчерпан) → неполное обязательное ревью: `final_status = manual_review_required_on_v<N>` → `client_readiness` (никогда не `approved`; при `failed_reviewers == все` — reason `all_reviewers_failed`);
   3. `N ≥ 2 ∧ coverage_N == coverage_{N-1} ∧ substance_blockers_N > substance_blockers_{N-1} ∧ ∃ новый substance-блокер с evidence, отсутствовавший в N−1 (по `section_id`+категория)` → regression: `current_draft_path = drafts/v<N-1>.md`, `forced_exit_on_v<N-1>_with_remaining_issues` (в Brief недостижима; тест — только Full); при несопоставимом покрытии regression не проверяется;
   4. `substance_blockers == 0 ∧ form_blockers == 0` → `approved_on_v<N>` → `client_readiness`;
   5. `substance_blockers == 0 ∧ form_blockers > 0` → `accepted_early_on_v<N>` (form-блокеры → баннер) → `client_readiness`;
   6. `N < max ∧ ∃ blocker с evidence из deterministic/citations/hard_fail logic` → [медиатор, если блокеров/major ≥2 от ≥2 ревьюеров или есть `conflict`; иначе CLI собирает `mediator.json` сам] → pre-seed `drafts/v<N+1>.md` → dispatch writer → lint/citations → N+1;
   7. `N < max` без заземлённых блокеров → `accepted_early_on_v<N>` + баннер;
   8. `N == max` → `forced_exit_on_v<N>_with_remaining_issues`.
   9. Проверяется **перед** веткой 8 (D-165, прогон 2026-09-16): `N == max ∧ form_blockers == 0 ∧ 0 < substance_blockers ≤ 2 ∧ все substance-блокеры подняты `citations` (`source_reviewer` или `provenance[]`) с `issue_category = unsupported_claim` ∧ `attempts.targeted_fix == 0`` → точечный проход: `attempts.targeted_fix++`, `targeted_fix = {iteration: N+1, reviewers: ["citations"]}`, pre-seed `drafts/v<N+1>.md` и dispatch writer с инструкцией «для каждого названного пункта добавить токен источника, где норму содержит источник пакета, иначе снять утверждение или оговорить его как нерешённое; больше ничего» (D-208); на итерации N+1 диспатчатся и агрегируются **только** эти ревьюеры (без stub’ов для остальных), дальше ветка 4 (`approved_on_v<N+1>`) или ветка 8 (`forced_exit_on_v<N+1>_with_remaining_issues`); второй раз за прогон не срабатывает.
   **Открытые существенные замечания (D-210).** Каждая ветка, уводящая в `client_readiness` (2, 3, 4, 5, 7, 8), рядом с `remaining_blocking_issues` (только блокеры) пишет `state.open_substance_majors` — `major` содержательных рецензентов, открытые на поставляемой версии: `version = regression_to` на ветке 3, иначе `N`; ветки 1, 6, 9 поле не пишут. Выход «писатель не изменил черновик» (D-153) пишет его для `v<N−1>` — версии, которую поставляет экспорт. Строки считает `review.open_substance_majors(state, version)`: классы — `logic`, `citations`, `counterarguments` (`form` — не класс); учитываются записи `iterations[]` с `iteration ≤ version`; для каждого класса вытесняющая запись — последняя, в `coverage` которой он есть, поэтому класс, упавший позже (`failed_reviewers`) или не перезапущенный точечным проходом ветки 9, сохраняет свои `major` — отсутствие в частичном ревью не закрытие. Из вытесняющей записи берётся каждый хранимый issue с `severity = major` и `tier = substance`, среди участников которого (`provenance[]` + `source_reviewer`) есть класс, для которого эта запись вытесняющая, — одна строка на issue (два issue одного раздела и категории с разным текстом — две строки); `class` — первый такой участник по `SOURCE_PRECEDENCE` (`citations`, если он среди них), `reviewer` — хранимый `source_reviewer`. Строка: `{id: om-<n>, class, reviewer, section_id, category, issue_category, issue, issue_client, suggestion, from_iteration, origin: loop, status: open}`; порядок — итерация, раздел в порядке документа, позиция в записи; словарь `status` (`open|resolved|unresolved|manual_review|left`) и `origin: recheck` общие с проверкой готовности. `summary.md` печатает строки разделом «Open reviewer findings» (`memo.summary.open_reviewer_findings`) сразу после списка блокирующих: `status` ∈ {`open`, `left`, `unresolved`}, кроме строки `citations` с `origin: loop` и `status: unresolved` — она переносится в `remaining_blocking_issues` и дважды не печатается; формат `class · origin · status · section_id · category · issue` (сырые id), пусто — `none`. Сам раздел есть только в `summary.md`.
5. Медиатор: вход — issues всех ревьюеров; выход `reviews/v<N>-mediator.json` (`instructions[] {section_id, source_reviewer, category, severity, instruction, resolution?}`, `dropped[]`); md рендерит CLI. Приоритет: substance > form; внутри substance — накапливать. Инструкция, говорящая писателю, что содержит источник, несёт фрагмент `source_evidence` рецензента; issue без него передаётся как «снять или оговорить», никогда как «пересказать» (D-208).
6. **Открытые замечания на последнем чтении (D-211).** Только при непустом `open_substance_majors`; пустой список оставляет `client_readiness` прежним. **Проход 1:** readiness получает `${open_findings}` (строка на запись `id · class · section · issue · suggestion`, без привязки к `draft_sha`) и правила в шаблоне: это не повторное ревью; каждая строка лупа — строка `dispositions[] {id, action: polish|manual_review|leave, note}` (необязательное поле `client-readiness.schema.json`); `polish` для любого класса — issue на раздел строки «снять или смягчить утверждение, без новой нормы и без нового источника» (у CIT-04 снять пинпойнт при том же id — смягчение); `citations` — `polish`/`manual_review`, `logic`/`counterarguments` — `polish`/`leave`; отсутствующее или недопустимое распоряжение — `manual_review` для `citations`, `leave` для остальных. Код читает `dispositions` только первого прохода: `manual_review`/`leave` сразу дают `status` `manual_review`/`left`, строка `polish` остаётся `open`. Новых id чеклиста нет. **Правка:** диспатч polish публикует базу `reviews/v<N>-prepolish.md` (`by: command`, идемпотентно, после появления шага не заменяется). При первом входе после писателя polish, до lint, `polish_scope_errors` сравнивает базу и результат по собственным строкам разделов (грамматика языка мемо; строки до первого заголовка — `preamble`): изменённый раздел вне разделов issues readiness с потомками и разделов `executive_summary`/`conclusion`/`recommendations` — ошибка; issue на `document` снимает ограничение по разделам; выросший набор id `[[src:]]` любого изменённого раздела — ошибка всегда. Итог — `state.polish_check {draft_sha, errors}`, lint-fix вне проверки; база или черновик, которые нельзя прочитать как опубликованные, — проваленная проверка (`baseline_unavailable`/`draft_unavailable`, и перед перепроверкой тоже). Ошибка — одной записью state: база обратно на канонический путь черновика (`current_draft_path`), строка `draft_versions[]` выровнена по отчётам для sha базы, `export_pin {version, sha256}`, `export` с причиной `polish_out_of_scope`: `approved`/`accepted_early`/`client_ready_on_vN` → `manual_review_required_on_v<версия>`, иная метка сохраняется. Без базы пин называет последнюю версию, чьи байты на диске видел цикл ревью, а без такой версии пина нет и экспорт выбирает как обычно, под ручной проверкой. `export_draft_sha` и выбор черновика в `finalize` (`select_draft` без `--draft-sha`) отдают `export_pin` раньше флагов проверок, сопоставляя версию и sha. **Перепроверка:** если правка изменила раздел, держащий строку `polish` любого класса (раздел строки и потомки; строку `document` — любой изменённый), после чистых lint/citations один раз (`MAX_POLISH_RECHECK = 1`) диспатчится `citation-auditor` в слот `citations_polish` (только имя слота и пути, не вид ревьюера; выход `reviews/v<N>-citations_polish.json`, чеклист `citations`, `${lookup_budget}` 20, строка `${recheck_scope}`, ответ `resolutions[] {id, status: resolved|open, note}`); ретраи — штатный `reviewer_json_retry` по ключу `<N>:citations_polish`. `read_polish_recheck` валидирует его как `citations` для sha после правки; строка `dispatch:citation-auditor` (`ok` или `fail`) идёт ко второму проходу, минуя `_readiness_degraded`. Пригодна перепроверка опубликованная, не заглушка, валидная, не `downgraded`, без `unverified_hard_fail` и без блокера на `document`; строка `polish` `resolved` только при пригодной перепроверке, её `resolved` в `resolutions` (повторённый `id` не читается ни в `resolutions`, ни в `dispositions`) и без блокера в её разделе и потомках, иначе `unresolved`. Блокеры любой опубликованной, не заглушечной, схемно-валидной перепроверки для этого sha (`downgraded` тоже, синтетический включая) сохраняются всегда; новый `major` — строка `origin: recheck`, `status: open`, только `summary.md`. **Проход 2** — как прежде, со статусами строк и строками `recheck` «для сведения». **Переход в `export`** (любой выход `client_readiness`, и отмена прогона в этой фазе до `finalize` — отмена сначала проводит опубликованную правку через ту же проверку границ и, при ошибке, через тот же возврат базы и закрепление экспорта, без диспатча агентов): строка `polish` без завершённой правки и пригодной перепроверки — `unresolved`; строки `citations` лупа в `manual_review`/`unresolved` → `remaining_blocking_issues` (`major`, с `issue_client`), причина `open_substance_majors`; блокеры перепроверки → туда же как написаны, причина `polish_recheck_blocker`; если что-то добавлено, `approved`/`accepted_early`/`client_ready_on_vN` → `manual_review_required_on_vN`, `forced_exit…`/`manual_review_required…` сохраняют метку и получают причины. Строки `logic`/`counterarguments` в `left`/`unresolved` и строки `recheck` — только `summary.md`, статус не меняют.

### 4.7. Язык (D-168…D-179)

Две независимые настройки на одном наборе языков `en`, `de`, `fr`, `es`, `ru`: язык мемо (`memo_language`, default `en`) и язык интерфейса (`ui_language`, default `auto`). Значение `auto` разрешает роутер: Python язык не определяет.

- **Пакеты.** Английские строки живут в коде (`scripts/memoforge/i18n_en.py`, словарь `EN`) — это пол для always-deliver, включая `finalize --salvage`. Остальные четыре языка — `lib/i18n/<code>.json` с тем же деревом ключей (`memo`, `ui`). Доступ только через `memoforge/i18n.py`. Отсутствующий ключ → значение `EN`; паритет-тест держит пакеты равными `EN` по ключам и плейсхолдерам.
- **Выбор.** `mf task new --language <code>` и `--ui-language <code>` — явная просьба пользователя (неверный код отклоняется с перечнем допустимых, как у прочих enum-опций); `--detected-language <code>` — язык, на котором пишет пользователь, применяется только к опции, разрешившейся в `auto` (вне набора → `en`). Неверное значение из окружения или `options.json` → `en` + событие `language_fallback`. `task new` возвращает `language`, `ui_language` и источник каждого.
- **State.** `language` — enum пяти кодов; `ui_language` — необязательное поле (отсутствие = `en`). `mf task language --workdir <dir> [--memo <code>] [--ui <code>]`: язык мемо меняется, пока план не утверждён (иначе `language_locked`; проверка — под блокировкой state), язык интерфейса — в любой нетерминальной фазе.
- **Нативное написание.** Writer пишет на языке мемо; ревьюеры, citation-auditor, mediator и research-sufficiency-reviewer получают `${memo_language_name}`. Находки (`issue`, `suggestion`) остаются английскими; блокер вне `en` несёт необязательное `issue_client` — одно предложение на языке мемо, которое печатают Status и summary (для `en` поле удаляется при валидации ревью). Поля, попадающие в деливерабл дословно (`drafting_warnings[]`, `blocking_gaps[].gap`, `why_blocking`, `out_of_scope_gaps[]`), пишутся на языке мемо.
- **Распознаватели.** Lint, аудит цитат и разбиение на предложения читают `lint.Grammar`, построенную из пакета (заголовки секций, литерал строки риска, дисклеймер, плейсхолдеры, сокращения, отключённые правила — `L-03` для `ru`). Для `en` отчёты байт-в-байт прежние.
- **Деливерабл.** Метки md/docx, заголовки жёлтого баннера, `summary.md`, `fallback-summary.md`, публикуемый `source-pack.md`, тексты баннеров (по `banner_id` + `params` в момент рендера; легаси-строка без `params` печатается сохранённым текстом) и три предупреждения кода — из пакета языка мемо; docx получает `w:lang`. Места обратного разбора (`condense_appendix`, `_without_status`, `docx validate`) читают те же значения, что и рендерер. `status_signature` для `en` прежняя, для остальных языков язык входит в хеш.
- **Цитаты.** Токены `[[src:<id> <pinpoint>]]` — всегда в канонической английской форме; метки пинпойнтов, `ibid`, месяцы и подписи annex переводятся только при выводе, после логики якорей и ibid. Форма цитаты OSCOLA (`Case`, суды, виды актов, `(n N)`, `CELEX/ECLI/ELI`) не переводится.
- **Отказы.** Пакет языка мемо не читается: `task new` / `task language` / обычные `render` и `finalize` → `language_pack_unavailable: <code>` (язык мемо молча не подменяется никогда); `finalize --salvage` доставляет с английскими генерируемыми строками и явной строкой об этом в summary. Нечитаемый пакет интерфейса → английский интерфейс.
- **Язык интерфейса** (`ui_language`, D-176, D-176a, D-177, D-178, D-178a, D-176b). Английские строки интерфейса — в `EN["ui"]` (`phases`, `gates`, `machine`, `dashboard`, `sources`, `preflight`, `banners`, `language_names`), остальные четыре языка — секция `ui` пакетов; нечитаемый пакет для `ui.*` тихо даёт английский. Гейты: `gates.render*` и `build_auq` печатают текст, вопросы, `header`, подписи и описания кнопок на языке интерфейса; машина видит только канонические значения — `parse_auq(answers, ui)` переводит заголовки и подписи через обратную карту `canonical_map(ui)` до прежних проверок (`Cancel` сохраняет приоритет, незнакомая подпись никогда не утверждает; канонический английский принимается при любом `ui`; карта не выдаётся в CLI-ответ). Токены текстового канала (`approve`, `edit:`, `proceed`, `1A`…) не переводятся. Строка `Язык мемо: <эндоним>` в карточке плана — только когда язык мемо или интерфейса не `en` (D-172). Дашборд: патч несёт `labels` (весь `ui.dashboard`), подписи фаз/шагов/статусов, текущую строку и уведомления на языке интерфейса (уведомления — через `ui.banners.<id>`, без параметров запуска, D-88); `lib/dashboard.html` читает `labels` с английским запасом `EN_FALLBACK`; `progress.last_line` в state остаётся английской (§10). Дайджест гейта 11 и блок preflight — из пакета; машинные токены и `${source_access}` для агентов — английские. Агенты пишут видимые на гейтах поля (вопросы intake, `issues[].title/question`, `notes`, follow-up) на языке интерфейса; `header`, `issue_id`, `layer`, `classification`, `estimated_complexity` — канонические. Скиллы отвечают на языке интерфейса (переводят свою прозу, `chat_line`, терминальный текст; гейтовые `text`/`questions`, пути, команды и токены — дословно); `--ui-language` только по явной просьбе; при возобновлении в новом чате роутер читает `ui_language` из state; `edit: memo in French` на плановом гейте идёт в `mf task language`, минуя `gate parse`. Английские гейты, AUQ-объекты и патч дашборда (кроме `labels` и `chat_line`) байт в байт прежние.

### 5.3. Реестр источников и цитат (M5, M6)

`research/sources.json`: `{schema_version, sources: {<source_id>: {layer, title, citation_form, identifiers {celex?, ecli?, eli?, reporter_cite?, neutral?}, url, retrieved_at, retrieval_tool, provenance: agent_saved|confirmed (confirmed = `liveness` получил тело по `url` и его sha совпал с `raw_sha256`), tier, raw_path|null, raw_sha256|null, raw_chars, meta {in_force?, effective_date?, status?} (из ответа инструмента, как передал агент), liveness {status: ok|redirect|dead|changed|unchecked, code, checked_at}, verification {us: resolved|unresolved|ambiguous|n/a, us_by: agent|cli|null, eu_syntax_ok: bool, checked_at} (единая enum для всех предикатов C-04, digest'а гейта 11 и баннеров; `us_by` — только происхождение), currency {status, checked_at, note}|null, pack {role_by_issue{}, weight, confidence, use_in_memo}|null}}}`. Опциональное поле `raw_kind` (закрытый enum `full_text|excerpt|agent_summary|client_file|none` (D-200)) — что за текст сохранён: `full_text` пишет только код (`mf sources save`), `register --raw-file` по умолчанию `agent_summary` (`--raw-kind` принимает только `excerpt|agent_summary|client_file`, `full_text` и `none` отвергает сам парсер), поверх записи `full_text` регистрация с `--raw-file` отказывает `source_is_code_saved` и ничего не пишет. Умолчание живёт в читателе (`raw_kind_of`: поле, иначе `agent_summary` при наличии raw, иначе `none`; после заморозки авторитетна запись пакета через `pack_raw_kind`), а не в данных — старая папка и старый пакет валидны и не переписываются. Заморозка верит файлу: у записи `full_text` digest файла сверяется с записанным до перезаписи `raw_sha256` — расхождение понижает запись до `agent_summary`, пропавший файл — до `none`, каждое понижение даёт предупреждение `full_text_integrity` в ответе `pack --freeze` и строкой-исключением дайджеста гейта 11. Опциональные поля `raw_original_path`/`raw_original_sha256` (D-201) — POSIX-путь и sha256 оригинала, сохранённого байт в байт так, как его отдал сервер (PDF); пишутся и снимаются только вместе, у текстового источника отсутствуют. Именно `raw_original_sha256`, а не `raw_sha256`, отвечает на вопрос «те же ли это байты» для такой записи (у PDF без текстового слоя текстового digest нет вовсе), и именно его сверяет liveness. Заморозка верит файлу и здесь: digest оригинала пересчитывается с диска в `snapshot[].raw_original_sha256` (пропавший файл — строки нет), расхождение или пропажа дают то же предупреждение `full_text_integrity`, а понижение `raw_kind` — только для записи `full_text`: у записи `none` понижать нечего. Опциональное поле `retrieved_from` (строка) — адрес MCP-эндпойнта, которым был непубличный `url` (D-192): при регистрации `url` на хосте из `sources.NON_PUBLIC_SOURCE_HOSTS` в `url` не попадает, уходит в `retrieved_from` как `<scheme>://<host><path>` (без query), результат несёт `warnings: ["url_not_public"]`; у любого другого URL снимаются параметры-креденшелы `sources.AUTH_QUERY_PARAMS`. Хост с процентом (`mcp%2ecasus%2elegal` — `%2e` переживает `urlsplit(...).hostname` нерешённым) — не адрес вовсе: он канонизируется в ничто, поэтому запись не хранит `url`, а текст чистится в `[address removed]`; процент в пути или query (`https://sudact.ru/regular/doc/%D0%90/`) — норма и работает как раньше. `dedup_key` считается по очищенному URL. Занятый явный `--id`, чья запись не несёт хэша ни с одной стороны (citation-only, `background`), принимается только при совпадении dedup-идентичности — иначе `source_id_collision`, и ничего не пишется. `retrieved_from` клиенту не печатается и не выгружается. При приёме `--raw-file` текст чистится до вычисления sha (D-193): URL на непубличном хосте → `[retrieved via <сервер>]`, у остальных снимаются те же параметры. `slugify` транслитерирует кириллицу до ASCII-свёртки (D-194). Пишет только `sources.py` под `sources.lock` (протокол как у `state.lock`). `research/quotes.json`: `{quotes: {<quote_id>: {source_id, raw_sha256, text, char_start, char_end, lang, words}}, skips: [{section_id, source_id, reason, at}]}` (схема `quotes`).
**«Код сохранил целиком» (`source_text.py`, D-203).** Полноту и принадлежность текста решает код, а не агент: `source_text.verdict(text, layer=…, expect_number=…, expect_date=…, expect_article=…)` отвечает `{raw_kind, outcome, error, found}` по одному лишь тексту — без сети, без реестра и без флага юрисдикции (российский акт опознаётся по самому тексту). Документ начинается не с начала страницы: выше лежат меню портала и заголовок портала, чья дата у sudact на день раньше, поэтому `document_start` берёт первую строку-заголовок вида акта (`ОПРЕДЕЛЕНИЕ`, в том числе вразрядку, с хвостом вроде «ПОСТАНОВЛЕНИЕ арбитражного суда кассационной инстанции» и с одним квалификатором из закрытого списка «апелляционное, кассационное, надзорное, частное, дополнительное», но без «от <дата>» и «по делу») либо строку «Именем Российской Федерации»; в текстовом слое PDF резать нечего, и зона начинается с нуля. Зона номера идёт от начала документа до первого «установил(а)» (или `HEADER_ZONE_CHARS = 2500`, что раньше) и дополнительно **назад** — не более `PRE_HEADING_LINES = 8` строк и `PRE_HEADING_CHARS = 600` знаков, до заголовка портала или «хлебных крошек», потому что у актов ВС номер напечатан выше заголовка и в теле не повторяется; зона даты идёт только до первого «рассмотрев/рассмотрела/изучив» (у определения судьи о передаче обжалуемые акты перечисляются за «изучив» ровно так же, как за «рассмотрев»; потолок `HEADER_ZONE_CHARS` остаётся для текста без всех трёх — постановления Пленума) и назад не расширяется никогда, поэтому ни ранняя дата портала, ни дата обжалуемого акта не могут сойти за дату самого акта. Номер сверяется целым токеном (пробелы, тире, `№`/`N`/`No` и `ё` нормализуются; `305-ЭС24-8702` ≠ `305-ЭС24-8702 (1,3)`), дата — цифрами, ISO и русскими словами (две даты шапки засчитываются обе, даты из списков — нет). «Целиком» означает положительный признак: резолютивный маркер отдельной строкой после первого «установил(а)» либо «постановляет» в шапке и закрывающая подпись Пленума; для `statutes` — заголовок запрошенной статьи целым токеном (`152` ≠ `152.1`) и тело до следующего заголовка ≥ `ARTICLE_BODY_MIN_CHARS = 200`; для `doctrine` — длина ≥ `FULL_TEXT_MIN_CHARS_DOCTRINE = 2500`; для нероссийского `case_law` — длина ≥ `FULL_TEXT_MIN_CHARS_CASE = 4000` и `--expect-number` целым токеном в первых `HEADER_ZONE_CHARS` знаках. Неопределённое остаётся `excerpt` — эвристик «навигации» и «последней трети» нет. Для российского судебного акта отсутствие номера или даты в своей зоне — отказ `requisites_mismatch`, и вызывающий не регистрирует ничего; та же неудача вне российского правила — всего лишь `excerpt:identity_unverified`, не отказ.
**`mf sources save` — текст источника сохраняет код (D-199).** `mf sources save --workdir … --layer … --title … --citation … --tier … (--url <адрес> | --resolve vsrf|sudact) [--id] [--meta] [--identifiers] [--expect-number …] [--expect-date …] [--expect-article …]` плюс общие с `fetch` `--method/--json/--accept/--lang/--timeout`; сохранение не методом GET (маршрут Normattiva, `POST`) обязано нести `--public-url <публичная страница документа>` — эндпоинт отвечает многим документам по одному адресу, поэтому ни одного не называет и клиенту ничего не открывает: без флага (или с адресом, который клиенту давать нельзя, `url_error`/`url_not_public`) — отказ `public_url_required` до любого запроса и записи, у GET флаг не принимается (`public_url_requires_post`: выбранный адрес и есть публичный); эта страница — `url` записи, поэтому идентичность, поиск дубля и ссылка клиента называют один документ, а эндпоинт и метод хранятся в `meta.save_endpoint`/`meta.save_method` (только код: `--meta` агента их отбрасывает, `register` отказывает; финальное ревью, A); `--resolve vsrf` и `--resolve sudact` ищут адрес по реквизитам сами (D-202), шагом скрипта команда не является (`state.json` не трогает, `--step`/`--attempt` не принимает). Транзакция из трёх шагов, замок `sources.lock` — **только на первом и третьем** (исследователей трое, сеть долгая, `LOCK_TIMEOUT` = 30 с): (1) проверки реестра — заморозка (`sources_frozen`), идентичность занятого `--id` (`source_id_collision`: та же нормализованная `citation_form` или тот же нормализованный url — идентичность D-206, а не похожесть), слой (`source_id_layer_mismatch`); ничего не пишется; (2) без замка — вежливый темп по хосту, `url_error`, allowlist на адресе **и на каждом хопе редиректа** (`RedirectGuard`), ответ; допуск: `unchecked`/`dead`/интерстициал (`interstitial`)/заглушка доступа (`access_stub`) — регистрации нет, усечённое тело — отказ `truncated` (частичный документ не бывает выдержкой): потолок `LIVENESS_MAX_BODY_BYTES`, тело короче объявленного `Content-Length` (ограниченное чтение не падает, и обрыв виден только по обещанию сервера — считается по байтам с провода, до `_inflate`; значение заголовка обрезается по краям, потому что `Content-Length: 3661 ` парсер принимает) и ответ `206 Partial Content`; правило живёт в транспорте, поэтому `fetch` получает его тоже, тип, который не текст и не PDF, — `unsupported_media_type` (D-201: PDF идёт своим путём, а PDF — это тело с сигнатурой `%PDF-` в первых 1024 байтах, что бы ни объявлял заголовок, — одно правило `sources.is_pdf` для сохранения и резолвера; одна сигнатура, не определитель типов; объявленный тип читается один раз, `sources.declared_type`: пустой или битый тип/подтип, `application/`, — не объявлен ни для правил интерстициала, ни для допуска; финальное ревью, B); HTML → `markup_to_text`, `prepare_raw` **один раз** на converted-тексте (поэтому сохранённый digest — тот самый, который пересчитывает liveness), затем `source_text.verdict` (D-203), `requisites_mismatch` — отказ; принятые байты пишутся во временный файл **внутри целевой папки** (`research/raw/<layer>/.<id|slug>.<pid>.tmp`); (3) снова под замком — те же проверки заново, и только здесь поиск дубля по dedup-идентичности, выделение id (`--id` или `unique_slug`), проверка собранного кандидата по схеме, **затем запись реестра и только последней — публикация файла** `os.replace`. Две записи одной транзакцией не сделать, и порядок выбран по цене уцелевшего окна: публикация первой при убийстве процесса теряет прежний текст безвозвратно, а такой порядок оставляет реестр с digest, которого у файла ещё нет, и **прежние байты целыми** — ровно то расхождение, которое проверка целостности на заморозке (D-200) понижает с предупреждением `full_text_integrity`, а тройное равенство sha C-02 не пропускает в цитату. Громко и безопасно вместо тихо и с потерей; журнала и резервного файла нет. Временный файл удаляется в `finally` на любом пути. **Путь вверх:** поверх записи того же слоя и той же идентичности текст заменяется **только при исходе `full_text`** — либо когда запись не хранит текста вовсе — citation-only, предыдущий отказ или `raw_path`, чьего файла нет на диске (публикация, прерванная после записи реестра): «не хранит» читается с диска, а не по одному полю, поэтому следующий `save` чинит запись, а не отвечает пустым `idempotent` поверх отсутствующего файла; вытеснять нечего, и выдержка, сохранённая кодом, проверяема там, где не было ничего; при `excerpt:*` поверх уже хранимого текста остаётся прежний и пишется лишь `meta.save_outcome` (короткая выдержка не вытесняет длинную) — это история попыток, а исход **хранимого** текста — `meta.text_outcome`, который пишется только при публикации текста (только код; `register --raw-file`, заменивший текст, и сохранение, оставившее запись без текста, его снимают; финальное ревью, E); поверх записи `full_text` выдержка — отказ `source_is_code_saved` (понижение), другие байты — `source_id_collision` (он же ответ проигравшему гонку за тот же url; при совпадении digest — `idempotent` с id победителя). Отказ или сбой не меняет ни файлов, ни записей; единственное исключение — `meta.save_outcome` в **уже существующей** записи, и только когда она доказанно тот же источник (проверки шага 1 повторяются и здесь: занятый тем временем `--id` чужой записи не штампуется): `full_text` | `excerpt:<причина>` | `refused:<причина>` (`unchecked`, `dead`, `interstitial`, `access_stub`, `truncated`, `pdf_truncated`, `host_not_allowed`, `unsupported_media_type`, `requisites_mismatch`, `url_error`, `captcha` — D-202, редирект в капчу sudact.ru); отказы со стороны реестра (`sources_frozen`, `source_id_collision`, `source_id_layer_mismatch`, `source_is_code_saved`) не пишут ничего. Запись получает `retrieval_tool = "mf-save <host>"` (в `BODY_COMPARABLE_TOOLS`, поэтому liveness сверяет тело и может поднять `provenance` до `confirmed`), `raw_kind` из вердикта и `provenance: agent_saved`. `idempotent` — «запись уже была **и** адрес отдал те самые байты, которые она держит»; маркер «те же байты» — `raw_original_sha256`, если запись его несёт, иначе `raw_sha256`, и никогда наличие файла на диске (иначе запись со сканом отвечала бы `idempotent` поверх только что отброшенных чужих байт, и два разных документа считались бы одним). Публикация остаётся дисковой — новая запись, исход `full_text` или запись, не держащая на диске ничего, — но замена пропавшего файла другими байтами не починка, и ответ говорит `idempotent: false`. Ответ — `{source_id, created, idempotent, layer, raw_path, raw_sha256, raw_chars, raw_kind, raw_original_path, raw_original_sha256, save_outcome, url, host, status, code, bytes, provenance, tier}`, на отказе `errors`/`hint`. **`full_text` значит «документ сохранён кодом целиком в том виде, в каком его отдал сервер»** — это не утверждение о подлинности сайта.

**PDF приходит байтами, текстовый слой — удобство (D-201).** Ответ, чьё тело несёт сигнатуру `%PDF-` в первых 1024 байтах, **что бы ни объявлял `Content-Type`** (финальное ревью, B: одно правило `sources.is_pdf` — то, что задача 6 доказала на реальной цепочке, — для резолвера и сохранения; реальный `2394482.pdf` под `application/octet-stream` и под `text/html` — PDF для обоих, а тело без сигнатуры под `application/pdf` — не PDF и оригиналом не сохраняется), сохраняется **как отдан**: `research/raw/<layer>/<id>.pdf`, `raw_original_path` + `raw_original_sha256` по этим байтам. Через `prepare_raw` PDF не идёт никогда — она декодирует `utf-8-sig` с `errors="replace"` и испортила бы файл. Усечённый PDF — отказ `pdf_truncated` (те же три причины, что и у `truncated`), и не пишется ничего. Текстовый слой снимается **один раз**, на месте, `sources.extract_pdf_text` (импорт `pypdf` внутри функции), проходит `prepare_raw` как любой текст, кладётся в `<id>.md` = `raw_path` и судится `source_text.verdict` (у слоя PDF нет портала над документом, зона начинается с 0). Второго извлекателя нет: ни `pdftotext`, ни OCR. Слоя нет (нет `pypdf`, скан, нечитаемый файл) — оригинал сохранён, `raw_path: null`, `raw_kind: none`, исход `excerpt:pdf_text_unavailable`, личность **не** удостоверена: `[[q:]]` по такому источнику невозможна (C-02 не обходится), резолвер задачи 6 отказывает со списком адресов-кандидатов, а приложение печатает строку `memo.labels.pdf_unverified_note`. Идемпотентность, `source_id_collision` проигравшего гонку и защита от понижения считаются по digest **оригинала**; liveness сверяет тело только с ним и **не** принимает `sha256_normalised` (у оригинала нормализованной формы нет — это байты; для текстовых записей A7 не меняется); пара публикуется двумя `os.replace`, поэтому решение принимается **по каждому артефакту отдельно**: новая запись или исход `full_text` — публикуются оба; при `same_bytes` — тот из двух, который запись называет, а на диске его нет (починка, ответ остаётся `idempotent: true`); не `same_bytes` и на диске нет **ничего** — оба, `idempotent: false`; не `same_bytes`, но что-то лежит — не трогается ничего, пишется только `meta.save_outcome`. «Что-то лежит» — это **любая** из двух половин: уцелевший текст при пропавшем оригинале — это запись, которая что-то держит, и наоборот. Починка — это всегда только «тот же документ пришёл снова», поэтому она обусловлена `same_bytes` и ничем больше: закрыть пробел чужими байтами значило бы записать пару, которой как одного документа никогда не существовало, а заморозка потом пинует смесь не заметив — проверка целостности спрашивает лишь, совпадает ли каждый файл со своим digest, а после перезаписи совпадают оба. Что переиздано, у того и переписываются путь, digest и длина по фактически опубликованным байтам, поэтому запись никогда не описывает файл, которого у неё нет; «держит одно из двух» — третье состояние, которого одна булева переменная не видела, и убийство между двумя переименованиями чинит следующий тот же `save`. Выгрузка: `finalize.publish` копирует `sources/<id>.pdf` для `critical`/`supporting` **и когда `raw_path` пуст** — текст перестал быть единственными воротами; оба артефакта перечисляет одна `deliverable_source_files`, а `stage_source_files` их выкладывает. Порядок обратный прежнему: файл сначала **кладётся** в папку публикации, и digest берётся с **выложенной копии** — посчитать по исходнику и скопировать потом значит прочитать файл дважды, а между чтениями он может смениться (или исчезнуть, и тогда `copyfile` падал и рушил публикацию, чего D-109 не допускает); непроверенный файл при этом **никогда не лежит внутри папки, которую отдадут**: копия ждёт в отдельном каталоге рядом с публикацией, и внутрь переносится только та, чей digest сошёлся. Иначе отклонённая копия, которую не удалось удалить, уезжала бы к клиенту вместе с манифестом, где написано, что её не выгрузили; теперь неудачная уборка оставляет мусор там, где его никто не публикует. Копия, не прошедшая проверку, становится строкой-пропуском, упавший `copyfile` и неудавшийся перенос — тоже. `sources/source-pack.md` пишется **последним, из того же результата**, поэтому папка и её собственный манифест не могут расходиться. Тем же правилом закрыт текстовый экспорт: раньше `<id>.txt` выдавался по факту наличия файла, и правка `.md` после заморозки доходила до клиента (C-02 проверяет только то, до чего дотянулась `[[q:]]`, а источник с одним `[[src:]]` через неё не проходит); теперь текст сверяется с `snapshot[].raw_sha256` так же, как оригинал с `raw_original_sha256`, и выдаются **байты**, а не результат decode→encode: круговой прогон — лишний шанс разойтись с зафиксированным digest. У каждого артефакта своя строка пропуска — `memo.labels.text_export_mismatch_note` и `memo.labels.pdf_export_mismatch_note`: клиент ищет конкретный недостающий файл. После заморозки право на выгрузку даёт **только** снимок (заморозка не пишет digest у оригинала, которого не нашла, поэтому вернувшийся после неё файл не выгружается; пакет, который есть, но не читается, не даёт права ни на что — файл на диске значит, что заморозка была, а нечитаемые пины значат, что неизвестно, что она пинала), до заморозки (`--salvage`) файла пакета нет вовсе и отвечает digest записи. Расхождение, пропажа, «снимок не пинал» и «пакет не прочитан» — один факт для клиента и одна строка в `sources/source-pack.md`, написанная из **того же единственного наблюдения**, что и решение не копировать; **доставка продолжается** (D-109). **Слияние дублей оригинал не теряет** (финальное ревью, D): канонический id группы (D34-04) получает высший уровень группы (`critical` > `supporting` > `background`) — слияние не понижает ценность члена, и выгрузка, C-08 и приложение видят один уровень; канонический id, у которого своего оригинала нет, получает оригинал члена группы — первого по `canonical_of` среди тех, чей файл на месте, — и снимок пинует его под каноническим id тем же digest, что снят проходом целостности; псевдоним (`merged_into`) выгрузка не перечисляет вовсе: его представляет канонический, отдельно он не выдаётся и строкой «не совпадает с заморозкой» не называется — у псевдонима нет строки снимка по замыслу, и «нет пина» у него никогда не значило «изменён».

**`--resolve vsrf` — от реквизитов акта коллегии ВС РФ до адреса его PDF (D-202).** Только акты судебных коллегий; Пленум и Президиум — `save --url` с их опубликованной страницы. Канал: `GET <base>/lk/practice/acts?numberExact=true&actDateExact=off&number=<номер>` (`sources.VSRF_BASE`, по умолчанию `https://www.vsrf.ru`, инъецируемый — офлайн-тесты на `LocalServer`); ищется значение `--expect-number` с отброшенным хвостовым скобочным суффиксом (`\s*\([\d\s,]*\)$`), второго флага нет — искать широко, удостоверять точно: индекс портала суффикса не знает (`305-ЭС24-8702` → 8 ссылок, `305-ЭС24-8702 (1,3)` → 0), а удостоверение держит номер целиком, потому что суффикс отличает `(1,3)` от `(2,4)`; отбрасывается только в запросе российского резолвера (vsrf и sudact — один хелпер `resolve_query_number`), не в хелпере, общем с другими юрисдикциями. `--expect-number` и `--expect-date` здесь **обязательны**: без любого из них — `requisites_required: <флаг>` **до первого запроса** (в цепочке одного номера определение судьи о передаче и определение коллегии несут один номер и один скобочный суффикс). Ссылки `/lk/practice/stor_pdf(_ec)/<id>` собираются по байтам ответа, **дедуплицируются по адресу до потолка** `limits.RESOLVE_MAX_CANDIDATES = 10` и сохраняют порядок страницы. Листинг документом не считается: из правил интерстициала для него снято **только правило доли текста** (видимого текста 0.029 от байтов — ниже `LIVENESS_MIN_TEXT_RATIO`), а порог размера, `is_redirect_shell` и `is_access_stub` действуют — капча не читается как «страница без ссылок»; транспортный отказ (адрес отклонён, запрос не состоялся, ответ не индекс, тело усечено) поднимает `sources.ChannelUnavailable` → `channel_unavailable: <причина>`, а индекс, пришедший целым и не назвавший ни одного акта, → `requisites_mismatch` с пустым `candidates`: «ничего не нашлось» и «канал не работает» — разные факты. Заморозка проверяется до первого запроса — дешёвая предпроверка, а не гарантия (авторитетен отказ `run_save` под замком на шагах 1 и 3). Каждый кандидат скачивается под тем же вежливым темпом, тем же allowlist'ом и тем же `RedirectGuard` и удостоверяется по текстовому слою: `has_number` в зоне номера **и** `has_date` в зоне даты. «Разные» кандидаты — **разный digest нормализованного текстового слоя** (только схлопывание пробелов), никогда не байтов: один акт отдаётся под двумя id с разными байтами и одинаковым текстом. Капча не решается, не обходится и не повторяется: кандидат, пришедший не целым PDF (отклонён, не состоялся, не 2xx или вызов, усечён, или вовсе не PDF — нет `%PDF-` в первых 1024 байтах, что бы ни говорил `Content-Type`; сигнатура решает в обе стороны и раньше вердикта `interstitial_suspected`, так что подписанный скан, отданный как `text/html`, — всё равно скан), **сразу останавливает канал** — следующий кандидат не запрашивается, адреса не выдаются. Целый PDF без текстового слоя (скан) пропускается, а не вызывает отказ. Прошёл ровно один — сохраняется; несколько — `requisites_ambiguous` со списком адресов в `candidates`, ничего не пишется; ни одного — `requisites_mismatch` с `found` (деталь не пуста: `no candidate carries both`, если реквизиты встречались порознь) и тем же списком `candidates`, чтобы исследователь передал адрес в `save --url`. Резолвер **только выбирает адрес**: выбранный документ проходит транзакцию D-199 и PDF-путь D-201 без изменений (и потому скачивается ещё раз — записанные байты те, что получил сам `save`). Сохранение не методом GET (маршрут Normattiva, `POST`) хранит как `url` записи свой `--public-url`, а эндпоинт — в `meta.save_endpoint` (финальное ревью, A), и пишет `meta.save_method` — только код, при каждом принятом сохранении, чей запрос дошёл до адреса записи (публикация, ремонт, `idempotent`), для GET снимает, — и liveness такую запись не зондирует: `unchecked` с причиной `method_not_replayable`, а не ложное `dead` от эндпоинта, отвечающего `405` на HEAD и GET (D-205). Отказы резолвера не пишут ничего, включая `meta.save_outcome`: записи, к которой его отнести, ещё нет.

**`--resolve sudact` — штатный поиск sudact.ru, cookie сессии, опрос, капча и общий темп (D-202).** Акты арбитражных судов и судов общей юрисдикции. **Капча не решается, не обходится и не повторяется, никакая защита не обходится** (честный UA liveness, браузер не изображается). Канал: обычный `GET <base>/<раздел>/` открывает сессию, затем `GET <base>/<раздел>/doc_ajax/?<раздел>-case_doc=<номер>&page=1` с `X-Requested-With: XMLHttpRequest`, `Referer` и тем cookie, который поставила страница раздела, — cookie переносится, но **не требуется**: замер 21.09.2026 (три вежливых запроса контролёра, без вызова; ответы — фикстуры `scripts/tests/fixtures/sudact/`) — страница раздела не интерстициал (доля текста 0.526) и cookie не ставит, `new` — это 200, `finished` несёт список в `content`, а `total_found` — HTML-фрагмент, не число (`sources.SUDACT_BASE`, по умолчанию `https://sudact.ru`, инъецируемый — офлайн-тесты на `LocalServer`). Раздел — по номеру, одно правило имени: `А`/`A` (кириллица или латиница) + цифры + `-` + цифры + `/` + год (`А53-28950/2022`, `А40-630/25-100-1`) → `arbitral`, прочее → `regular`. Номер в запросе — `resolve_query_number`, как у vsrf; `--expect-number` и `--expect-date` обязательны (`requisites_required` до первого запроса). Ответ асинхронный: `{"status": "new"}`, затем `finished` со списком (HTML внутри JSON); после первого ответа не более `limits.SUDACT_POLL_MAX = 5` опросов, затем `channel_unavailable: not_resolved` — без исключения и без маркера. Кандидаты — `/<раздел>/doc/<id>/` спрошенного раздела (не `/doc/save|print|send/`) из HTML в `content` и только оттуда (`total_found` как счётчик не читается никогда; `finished` без `content` — вызов `no_content`), уникально, по порядку, до `RESOLVE_MAX_CANDIDATES`; названия и даты списка не читаются — метаданные sudact ставят акт на день раньше, дата только из текста документа в зоне даты. Каждый документ конвертируется так же, как в `run_save`, и удостоверяется тем же `certify_candidates`, что и кандидат vsrf (`requisites_ambiguous` не пишет ничего, `requisites_mismatch` отдаёт адреса). **Вызов на любом запросе** — страница раздела, поиск, каждый опрос, каждый документ, выборка самого `save` — пишет маркер `captcha: true` в `channels.json` и останавливает канал на весь прогон: следующий `--resolve sudact` любого процесса отвечает `channel_unavailable: captcha`, не сделав запроса. Вызов — редирект, который клиент не выполняет (на `/defence/` хоп отклоняется до запроса; вне allowlist; петля), ответ анти-бота или троттлинга (`202/403/429/503`, WAF, Cloudflare), HTML-страница, которую узнают правила интерстициала (все четыре), ответ поиска, который не JSON со строковым `status` (не «ничего не найдено»), страница документа, чей текст вовсе не российский судебный акт; к JSON поиска правила разметки не применяются. Транспортный отказ (таймаут, `404`, `500`, усечение) останавливает только этот вызов, без маркера; усечение судится раньше правил тела — короткое тело ничего не доказывает о вызове и хост не закрывает (в том числе при сохранении) — но вызов, названный статусом или заголовком (например, 202 с `x-amzn-waf-action`), закрывает хост при любой длине тела. `channel_unavailable` и `channel_budget_spent` адресов не выдают. **Темп — `<work_dir>/channels.json`** (`sources.channel_state_path`, вне глобов `research/*.json`, заморозка его не ставит во входы): `{"schema_version": 1, "channels": {"sudact": {"last_request", "requests", "captcha"}}}`, читается и обновляется **кратко под `sources.lock`** — слот `max(сейчас, last_request + CHANNEL_MIN_INTERVAL_S)` резервируется записью метки времени, **ожидание — вне замка** (три исследователя не стоят в очереди за удерживаемым замком). `limits.CHANNEL_MIN_INTERVAL_S = 2` и `limits.CHANNEL_MAX_REQUESTS_PER_RUN = 60` считают **каждый** запрос к хосту sudact.ru — резолвера (опросы включительно), любого `save` (по резолверу и `--url`), `fetch`, liveness и пробы preflight (финальное ревью, C); сверх бюджета — `channel_budget_spent`. Нечитаемый файл считается отсутствующим и перезаписывается, исключения не бывает; метка дальше, чем мог бы зарезервировать весь бюджет (`60 × 2` с), — отказ `channel_unavailable: clock`, без маркера и без запроса (не разрешение отправить и не ожидание до неё). После каждого ожидания и непосредственно перед отправкой состояние перечитывается под `sources.lock` (закрытый тем временем другим процессом канал ничего не получает — ни от резолвера, ни от сохранения на хост sudact); каждый прыжок редиректа, по которому пойдут, — тоже запрос канала (`RedirectGuard.hop`: слот, ожидание, счёт, перечитывание — в момент отправки прыжка, после того как urllib дочитал тело прежнего ответа, а не в момент решения; прыжок на исчерпанном бюджете не выполняется, `channel_budget_spent`). Резолвер только выбирает адрес и отдаёт его транзакции D-199; слот её выборки резервирует сама транзакция в момент отправки — как у любого сохранения на хост. **Сохранение по адресу, выбранному любым резолвером (vsrf и sudact), находит оба реквизита или отказывает** `requisites_mismatch`, не записав ничего — ни файла, ни записи, ни `meta.save_outcome` в существующую запись; и так — **любой** отказ сохранения на пути резолвера (`access_stub`, `unchecked`, `captcha`, `truncated`…): вторая выборка уже удостоверенного акта не переписывает историю хорошей записи, исход несёт только ответ; правило одно, в одном месте (`refuse` в `run_save`), а у обычного `save --url` исключение задачи 4 остаётся: вердикт отказывает только тексту, который читает как российский акт, и стену, HTML на месте PDF или скан иначе сохранил бы как выдержку (параметр внутренний, `run_save(..., resolved=True)`; обычный `save --url` не меняется); на sudact такое тело, вовсе не судебный акт, ещё и закрывает хост (`not_a_document`). **Стена — хоста** (`sources.sudact_address`): любое сохранение на sudact.ru — по резолверу или `--url` — не идёт по редиректу в `/defence/` (стоп в транспорте; страница капчи не запрашивается никогда; маркер, `channel_unavailable: captcha`, исход `refused:captcha`), любой другой встреченный им вызов (`interstitial`, `access_stub`, `unchecked`, редирект вне allowlist) пишет маркер, а после маркера сохранение на sudact.ru отказывает `channel_unavailable: captcha` до любого запроса. **Канал — это хост, кто бы ни спрашивал** (финальное ревью, C): запрос обычного `save --url`, `fetch`, liveness и пробы preflight к sudact.ru проходит ту же проверку маркера, ту же резервацию слота, темп и счёт и тот же стоп перед `/defence/` (`sources.sudact_transport`), а вызов, встреченный любым из них, пишет маркер (`sources.sudact_challenge_met` — порядок `sudact_refusal`: усечённое тело хост не закрывает); liveness записи на закрытом хосте или на исчерпанном бюджете отвечает `unchecked` с причиной (`channel_unavailable: captcha`, `channel_budget_spent`) и ничего не отправляет. Отсюда задача 9: после закрытия хоста — капчей или исчерпанным бюджетом — запасной путь LDH `RU/Sudact` регистрирует ответ самого LDH (`register --raw-file --raw-kind excerpt`), а не выбирает его адрес sudact.ru. Запасные пути кода не требуют: LDH `RU/Sudact`, веб-поиск агента → `save --url` с `--expect-*`.
`sources pack --freeze --step` — одна операция под `state.lock` → `sources.lock`: строит `research/source-pack.json` (роли/вес/уверенность из findings, currency, tier — без вывода веса из tier), фиксирует список `{source_id, raw_sha256}` snapshot'а, ставит `state.sources_frozen=true`, закрывает шаг. После этого `register` — exit 1; lint/audit/render читают только snapshot (регистрации, успевшие после pack, в snapshot не попадают и в меморандум не проходят).
**Верификации (до LLM, без новых сетевых клиентов):** `sources liveness` (stdlib `urllib` HEAD/GET, 10 с, best-effort; реестр читается под `sources.lock`, пауза, слот канала sudact и запросы — без замка, каждый результат пишется под коротким замком после перечитывания записи и не пишется поверх записи, изменившейся тем временем, — финальное ревью, раунд 2); `sources verify` — оффлайн: синтаксис CELEX/ECLI/ELI/neutral citation по регексам, `in_force`/`effective_date` из метаданных, сохранённых при регистрации из ответа LDH (`--meta <json>`), дубликаты по нормализованным идентификаторам. Существование US-цитат проверяет **сам `currency-checker` через CourtListener MCP** (`extract_citations`/`analyze_citations`) и записывает результат командой `mf sources verify --set <source_id> us=resolved|unresolved|ambiguous` (CLI сохраняет статус в ту же enum и `us_by: agent`). **«Не найдено ≠ выдумано»:** `unresolved` не удаляет источник; исключает его из `use_in_memo=rule` без второго подтверждения, попадает в исключения гейта 11 и в приложение.
Сопоставление цитаты (C-02): **только точное совпадение** текста blockquote с фрагментом `quotes.json` после узкой типографской нормализации (NFKC, схлопывание пробелов, унификация кавычек/тире/многоточий); дополнительно тройное равенство `quote.raw_sha256 == snapshot[source_id].raw_sha256 == sha256(текущий raw-файл)` и совпадение текста в диапазоне `char_start..char_end` (подмена raw или диапазона → блокер, без автообновления snapshot). После freeze `quote extract` работает только по версии raw из snapshot и отказывает (`raw_changed`), если файл изменился. Fuzzy (`difflib`) используется только внутри `quote extract` и `quote locate` для списка `candidates`, никогда — для успешного аудита. **Контракт extraction:** успех = точный диапазон, начинающийся и заканчивающийся на границах предложений, длиной ≤`max-words`; иначе ошибка без `quote_id` (`too_long` → `candidates` из sentence-bounded подфрагментов ≤`max-words`, если они существуют; `ambiguous` → позиции всех совпадений; `not_found`; `no_raw`; `raw_changed`). `mf quote skip --section <id> --source <id> --reason too_long|ambiguous|not_found|no_raw|raw_changed|already_used|other --note "<текст, обязателен при other>"` фиксирует в `quotes.json` осознанный отказ от цитаты для секции (`already_used` — единственный подходящий диапазон уже процитирован в другой секции; `other` — свободная причина, попадает в `drafting_warnings`). `mf quote locate --workdir <W> --source <id> --text "<слова>" [--context N] [--max-passages K]` (D-207) — **только чтение**: находит слова в сохранённом тексте источника (та же узкая нормализация и та же версия raw, что у `extract`, со snapshot'ом и merged-алиасами) и показывает место с окружением, ничего не регистрируя и не записывая `quotes.json`. Ответ всегда несёт `source_id`, `status` и `raw_kind`: `found`|`ambiguous` — `matches` и не больше `--max-passages` (3) отрывков `{char_start, char_end, match_start, match_end, text}`: окно ±`--context` символов (1500; больше 4000 — зажимается, не отклоняется), подрезанное по границам предложений так, что совпадение никогда не режется; `not_found` — `candidates`, 5 лучших фрагментов-предложений без потолка в 30 слов (предложение длиннее 1500 символов — его начало по границе слова), ранжированных без зависимости от длины: доля слов запроса (от 3 символов), найденных во фрагменте, при равенстве — fuzzy-сходство, затем позиция; `no_raw`|`raw_changed`|`unknown_source` — как у `extract`, с дайджестами. Exit 0 при любом статусе: ответ — данные.

### 5.4. Lint (`draft lint`; 14 правил, числа из `limits.py`)

Правила читают `document["grammar"]` — `lint.grammar(state.language)`, построенную из языкового пакета (§4.7); идентификаторы правил и пороги `limits.py` от языка не зависят, для `en` отчёты прежние.

L-01 предложения >40 слов; L-02 абзацы >3 предложений или >100 слов; L-03 em-dash вне «Term — definition»; L-04 AI-tells (`lib/ai-tells.txt`); L-05 уровни заголовков (H1→H2→H3, без H4/пропусков; заголовок не заканчивается `?`); L-06 биекция Exec Summary ↔ подсекции ↔ Conclusion + пункт Conclusion без вердикта риска (вердикт — в Risk line и summary-буллете; распознаватель `grammar.risk_verdict` не привязан к концу пункта, поэтому вердикт в начале или в середине (`Риск: средний (раздел 4.1).`) — тоже находка, D-189a); L-07 Risk-line формат и наличие; **L-08 blockquote: каждая блок-цитата с `[[q:]]`; ≤1 на подсекцию**; L-09 один и тот же фрагмент — не более одного раза в драфте, где фрагмент = `(source_id, raw_sha256, char_start, char_end)` (новый `quote_id` на тот же диапазон не обходит правило; один источник может цитироваться в нескольких секциях разными диапазонами); L-10 word cap для `executive-brief`: `слова тела + len(unique [[src:]]) × 12` ≤ 1200 (`major`); L-11 плейсхолдеры; L-12 секции шаблона и порядок; L-13 Exec Summary — буллеты ≤40 слов с `Risk:`; L-14 дисклеймер при `assumptions_accepted=false`. «Noun-phrase заголовки» и «конкретность рекомендации» — пункты чеклиста `form-reviewer`, не lint. Цитата необязательна; любая цитата проверяема (C-02); fixture двух секций (§4.4, §5.3, §5.4). Выход `lint.json` `{draft_sha, clean, findings[{rule, severity, line, section_id, excerpt, hint}]}`; `clean` = нет `blocker`.
`draft audit-citations` (все правила применяются и к источникам, полученным через `[[q:]]`→`source_id`): C-01 `[[src:]]`/`[[q:]]` в реестре и snapshot; C-02 `[[q:]]` == raw-фрагмент точно + `raw_sha256` совпадает; C-03 не `do_not_use`; C-04 `manual_check`/`unresolved` не в Risk-line/Exec Summary; C-05 freeze (источник в snapshot, `use_in_memo ≠ do_not_use`); C-06 pinpoint-формат; C-07 неиспользованные `rule`-источники (`major`, информационно); C-08 прямая ссылка `[[src:]]` на `critical`/`supporting`-источник без сохранённого текста (`raw_sha256: null` в snapshot), **а также** (D-204) прямая ссылка на `critical`-источник, чья запись **пакета** объявляет `raw_kind` не `full_text` и не `client_file` (`excerpt`, `agent_summary`, `none`) — `major`, одна находка на токен, никогда не блокер, отражается в приложении; запись пакета без поля (пакет заморожен до D-200) расширенного C-08 не получает; C-09 `pinpoint_not_in_raw` (D-204, `major`) — у `[[src:id <пинпойнт>]]`, чей источник `full_text`/`excerpt`/`client_file`, каждое напечатанное число пинпойнта стоит целым числом где угодно в сохранённом тексте собственного id (тот файл, что читает C-02; `152` ≠ `152.1`); проверяются номера статьи, пункта, подпункта, раздела, главы, приложения (`ст`, `п`, `пп`, `разд`, `раздел`, `гл`, `прил`) и `art`/`s`/`para`/`ch`/`reg`/`point`, освобождены страницы, `абз.`, `ч.`, recital, голое число, пинпойнт без цифр и римские цифры; грамматика — та же (`CYRILLIC_LABEL`, `PINPOINT`); находка несёт `source_id` и `pinpoint`; фильтр фантомов, не доказательство существования нормы. C-09 читается **только** `plan_drafting` для v1 (`machine._has_c09`): запускает обычный раунд lint-fix, один, если других дефектов нет, с инструкцией «исправить пинпойнт или убрать его»; `clean`, `citations_clean`, путь polish не меняются, баннер `lint_not_converged` из-за одних C-09 не поднимается, оставшиеся C-09 становятся строками приложения (§5.5), экспорт обычный. Выход `citations.json` того же вида, с `draft_sha`.

### 5.5. Docx-рендер (`docx/`)

- Парсер: `mistune` AST → хелперы python-docx (Arial 12, 1″, justify, 6pt, cyrillic rFonts).
- `[[src:id pinpoint]]` и каждая blockquote с `[[q:id]]` (через `source_id` цитаты) → цитата, форматируемая единственным билдером `oscola.py` (OSCOLA 5th, **D-150**): `compact` при первом упоминании инструмента (акта, решения, документа — не записи статейного реестра) и `short` при любом последующем упоминании любой его статьи, по классу источника (EU-legislation, национальное законодательство, CJEU, иные суды, soft law, доктрина), который определяется по `identifiers`/`meta`/`citation_form`; в теле ни одна форма не несёт URL, CELEX/ELI/ECLI и `retrieved …` (фолбэк при пустых полях — обрезанный `citation_form`, не склейка title+form), пинпойнты нормализованы (`art 6(1)(b)`, `para 89`, `s 2(1)`, `§ 26`), длина ≤ 120 символов. Метка считается меткой только перед настоящим номером — цифрой, `(` или целым римским числом (`art IV`, `art IV(2)`), поэтому `art Insurance para 1.7` меткой `art` не размечается (D-195). `display_pinpoint` — единственное место перевода метки: переводятся **все** канонические метки пинпойнта (`art 998 para 1` → ru `ст. 998 п. 1`), где бы они ни стояли, в любом регистре, с точкой или без (`Art. 998 Para. 1` → ru `ст. 998 п. 1`, en `art 998 para 1`), кириллический пинпойнт (метки `ст`, `п`, `пп`, `ч`, `абз`, `разд`, `раздел`, `гл`, `прил`) и текст в кавычках/ёлочках печатаются как написаны (D-186, D-195). Стиль цитирования — `citation_style` (front-matter шаблона, поверх него `config.citation_style`): **`inline`** (дефолт обоих шаблонов) даёт `(<цитата>)` гиперссылкой на зарегистрированный URL (`w:hyperlink` в docx, `[text](url)` в md) и не создаёт сносок; **`footnotes`** даёт настоящую сноску Word (`footnotes.xml`, `w:footnoteReference`, стили в шаблоне) на каждое упоминание, с обратной ссылкой `<short name> (n <номер первой сноски этого инструмента>)` в короткой форме. Два подряд идущих упоминания одного инструмента с тем же местом → `ibid` (footnotes) или снятие второй цитаты (inline). `[[q:id]]` удаляется из blockquote, её цитата выносится в строку атрибуции под цитатой. §Sources несёт по одной записи на инструмент в порядке первого цитирования: `<цитата инструмента> — CELEX/ECLI/ELI — cited at <все места, в порядке упоминания> — <канонический URL, без якоря статьи> — checked <date>, currency <status>` (статья со статусом `amended`/`repealed` называется отдельно); источник без публичного URL печатает на месте URL метку `memo.labels.retrieved_from_note` с названием базы (`routing.MCP_SERVER_LABELS` по хосту `retrieved_from`, иначе `memo.labels.legal_database`) и не несёт ни угловых скобок, ни гиперссылки на инлайн-цитате; URL на хосте из `sources.NON_PUBLIC_SOURCE_HOSTS` рендерер не печатает и не линкует даже из старой записи реестра (D-192); статейные заголовки не печатаются, инлайн-ссылка при этом может вести на якорь статьи; нумерация — по первой сноске (footnotes) либо по порядку цитирования (inline); §Sources и приложение «Unverified Sources» генерируются из snapshot, `verification`. `checked <date>` печатается только при успешной проверке ссылки — `liveness.status` ∈ `LIVENESS_SUCCEEDED` (`ok`, `redirect`); любой другой записанный статус (`dead`, `changed`, `unchecked`) и полное отсутствие записи о проверке дату снимают: источник, которого liveness не касался, не проверялся точно так же. Приложение перечисляет только источники, которые меморандум действительно цитирует: запись-заготовка, на которую нет ни одного токена `[[src:]]`/`[[q:]]`, в нём не появляется (D-197). Набор считается сканом выбранного черновика — и только им. Если черновика нет (salvage, переиспользованный экспорт), конвейер не гадает: `finalize.condense_appendix` оставляет блок «Unverified sources» готового экспорта как есть (он собран, пока черновик был, и уже отфильтрован), обновляя только `## Status`; если нет ни черновика, ни экспорта, deliverable'ом становится fallback-сводка и `unverified_rows(…, None)` печатает полный список, как до задачи 2 — в таком деградированном результате заготовка появиться может.
- **Приложение говорит, что за текст (D-204).** Строки по виду сохранённого текста цитируемого источника печатают оба рендерера (`SourceIndex.text_note` → `unverified_rows`): snapshot без digest у `critical`/`supporting` — `memo.labels.pdf_unverified_note`, когда заморозка закрепила оригинал PDF (`raw_original_sha256`: скан, оригинал сохранён и выдан), **вместо** `no_saved_text_note`, никогда обе; ни digest, ни оригинала — `no_saved_text_note`, как прежде (D-158: решает snapshot). Текст есть — `critical`- или `supporting`-источник (те же уровни, что у `no_saved_text_note`; C-08 оценивает только `critical`, приложение раскрывает), чья запись пакета объявляет `excerpt`, печатает `memo.labels.excerpt_note` («выдержка, а не документ целиком»), а при `meta.text_outcome: excerpt:no_reasoning` — `memo.labels.no_reasoning_note` («опубликована только резолютивная часть; мотивировки для проверки нет»): решает исход текста, который запись держит, а не `meta.save_outcome` — история попыток, которая движется и тогда, когда попытка ничего не опубликовала (финальное ревью, E); `agent_summary` — `memo.labels.agent_summary_note` («текст, который код не удостоверил как сам документ»); обе строки верны для любого производителя своего вида — ответ MCP, зарегистрированный как `excerpt`, кодом не сохранялся, а файл, сохранённый кодом и пониженный заморозкой до `agent_summary`, агент не копировал (финальное ревью, E); `full_text` и `client_file` — ничего; PDF с текстовым слоем судится по своему виду, как любой текст; запись пакета без поля — ничего. `client_file` с актуальностью `unchecked` строки актуальности не печатает и сам по себе в приложение не попадает: документ, который дал клиент, — не непроверенный источник (строка C-09 у него остаётся: это находка о пинпойнте мемо). Каждый C-09 **экспортируемой версии** — строка `memo.labels.pinpoint_not_in_raw_note` («пинпойнт {pinpoint} не найден в сохранённом тексте {source_id}») в строке своего источника, по одной на пинпойнт. Экспорт может выбрать более раннюю проверенную версию, чем последняя проверенная, а `citations.json` описывает только последнюю, поэтому находки C-09 вычисляет для выбранных байт тот, кто выбирает версию (`docx.exported_pinpoints` в `mf docx render` и в `finalize`), в действующем языке и режиме рендера (`finalize --salvage` при нечитаемом пакете рендерит на английском — и строки C-09 печатает), и передаёт их обоим рендерерам данными; рендереры модуль аудита не импортируют и `citations.json` не читают; только непредвиденный сбой вычисления стоит приложению строк C-09, но не экспорта (M9).
- **Ни один машинный код не доходит до читателя (D-197).** В docx, в md-fallback и в клиентских строках `summary.md` печатаются не коды, а слова языка мемо: `final_status` — через `memo.status_names.<семейство>` (семейство = код без версии `_on_v<N>`/`_v<N>`, версия подставляется как `{version}`: `approved`, `client_ready`, `accepted_early`, `manual_review_required`, `forced_exit_with_remaining_issues`, `delivered`, `failed`, `cancelled_by_user`, `fallback_summary_delivered`); `final_status_reasons[]` — через `memo.status_reasons.<код>`; строка блокера `blocker · s-5-1 · <текст>` — через `memo.severity.<код>` и слово раздела (`memo.labels.section_word` + `5.1`; `general`/`document` → `memo.labels.whole_memo`); статусы актуальности и ссылки — через `memo.currency_names.<код>` / `memo.link_names.<код>`. Неизвестный код печатается как есть — рендерер из-за него не падает. Сырые коды остаются в `state.json` и в технической части `summary.md` (строка статуса несёт и слова, и код в бэктиках; список блокеров там — с сырыми `s-<n>`).
- Списки: новый `w:num` на список; `2. Text` вне списка — абзац; вложенные bullets; экранирование `\|`; склейка soft-wrap.
- Баннеры статусов — как в v1. **Fallback (stdlib-only, без AST):** при отсутствии `python-docx`/`mistune` или исключении в рендере — `deliverable.md`: регекс-замена `[[src:…]]`/`[[q:…]]` на цитату того же стиля (`[n]` в footnote-стиле) с генерацией §Sources из snapshot; неизвестный/нерезолвимый id → `[unresolved: <id>]` + баннер; pandoc-ветка удаляется.
- `docx validate`: архив открывается python-docx; в `document.xml.rels` есть relationship на `footnotes.xml`; каждая `w:footnoteReference` имеет footnote с тем же id и ровно одну; число footnotes == число разрешённых упоминаний; каждая короткая форма ссылается на номер полной формы **того же инструмента** (`instrument` в карте сносок; карта строится рендерером и сверяется, для старых карт — по `source_id`); нет литеральных `[[src:`/`[[q:`/`[unresolved:` ни в одной части; стили `FootnoteText`/`FootnoteReference` присутствуют; каждая `w:hyperlink` ссылается на существующий relationship типа hyperlink в `document.xml.rels` (D-150). Провал → docx переименовывается в `memo-<slug>.invalid.docx`, главным deliverable становится md-fallback, баннер `docx_invalid`. Полная OPC/XSD-валидация не делается (минимализм §0.3a).
- Golden-тесты `document.xml`/`footnotes.xml`. Решение «python-docx + OXML, не docx-js» — ADR-05 в `docs/decisions.md`.

## §10. Пилот Workflow (за флагом)

`workflows/research.js` покрывает **только S3a** (фазы 5–6); `workflows/draft.js` — S4. S3b не представляется скриптом (маршрут 9→6 выходит из сегмента). `meta.phases` = фазы сегмента; каждый `agent()` получает путь к промпту, отрендеренному `mf dispatch render --step …`; агент **всегда** вызывает `mf report` в конце и обязан включить его ответ (`accepted`) в свой финальный текст; скрипт после фазы читает `steps[]` через агента-проверяющего и решает о ретрае. Критерии принятия: P1 = PASS в целевом окружении; прогресс виден в `/workflows`/Background tasks; `events analyze` показывает те же переходы, что router-путь. До этого `workflows/` не объявляется.
