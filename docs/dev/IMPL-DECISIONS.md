# Журнал решений реализации (дополняет ТЗ; писатели обязаны читать)

Формат: `D-nn — вопрос → решение (кто спросил / где применяется)`.

- D-01 — `research-sufficiency.overall_verdict`: значения `sufficient | targeted_followup_needed | insufficient` (нормативно §2.1; базлайновое `insufficient_for_client_ready_memo` не используется). Промпт `research-sufficiency-reviewer` обязан выдавать именно эти значения.
- D-02 — `sources[].pack.use_in_memo` и `source-pack.entries[].pack.use_in_memo`: enum `rule | application | risk | background | do_not_use` (как в базлайне `source-pack-builder.md`). Схемы `sources`/`source-pack` привести к этому enum (владелец — слайс S3 вместе с `sources.py`).
- D-03 — snapshot freeze (`{source_id, raw_sha256}[]`) живёт в `research/source-pack.json` (`snapshot[]`), `research/sources.json` остаётся `{schema_version, sources}`. `state.sources_frozen=true` + существование `source-pack.json` = freeze.
- D-04 — `research-findings.layer` допускает `preliminary` для `intake/preliminary-sources.json`; `methodology`/`considered_excluded` там опциональны; `_meta` обязателен всегда.
- D-05 — поле `intake-questions[].default_if_wrong` — источник строки «что изменится, если дефолт неверен» для `mf gate render --gate intake`.
- D-06 — `mediator.dropped[]` = `{issue, reason, section_id?, source_reviewer?, category?, severity?}`.
- D-07 — `client-readiness.json` содержит `reasoning` (первым) и опциональный `checklist[]` по `lib/checklists/client-readiness.json`; `mf review validate --kind client-readiness` проверяет набор id так же, как для ревьюеров.
- D-08 — `citations` issue_category = `source_drift | source_pack_mismatch | unsupported_claim` (существование/точность/currency — скрипт `draft audit-citations`).
- D-09 — идентификаторы чеклистов `LOG-/FRM-/CIT-/CTR-/CRD-` (см. CONVENTIONS); `review validate` требует равенства множества id с файлом чеклиста.
- D-10 — команда события для агентов: `${mf} events log --workdir <w> --event <name> --actor <agent_type> --data '<json>'` (сигнатура `events.py`; `tooling-core.md` использует `--event mcp_ratelimit_fallback`).
- D-11 — правила секций lint режим-зависимы по `config.template_id`: `classical-memo` — канонический список CONVENTIONS (L-12, L-06 биекция Exec Summary ↔ подсекции ↔ Conclusion, L-13); `executive-brief` — обязательны только `## N. Recommendations` и маркер sources (L-12), L-06 = биекция «подсекция ↔ пункт Recommendations», L-13 не применяется.
- D-12 — литеральный формат Risk-line: последний абзац каждой аналитической подсекции начинается с `Risk: high.|medium.|low.|undetermined.` (строгий регистр, точка), далее обоснование и рекомендация в том же абзаце; буллеты Executive summary (classical) заканчиваются на `Risk: <level>.`; L-07 — регекс `^Risk: (high|medium|low|undetermined)\.`. Шаблоны и `lib/prose-style.md` обязаны показывать этот формат литерально.
- D-13 — `state_io.write_state_unvalidated` существует только для `finalize --salvage` (M9 без jsonschema / повреждённый state); любое другое использование — нарушение M2 (grep-тест).
- D-14 — хуки пишут журнал через `memoforge.events.append_event` (тот же writer-протокол); `events.py`/`state_io.py` при импорте не требуют `jsonschema` (ленивый импорт в `schema.py`); `hooks_common.py` остаётся stdlib-only helper'ом поиска задачи.
- D-15 — `modes.resolve_config`: неизвестный `writer_model` → fallback `opus` + событие `writer_model_fallback` (никогда не исключение); событие `state_written` несёт `sha256` файла (для G3); `mcp_ratelimit_fallback` — тип события (в `EVENT_TYPES` и схеме); `intake-questions[].default_if_wrong` — обязательное поле; `task new --language` удалён (всегда `en`).
- D-16 — `schemas/style-meta.schema.json`: `confidence` принимает `number` (как пишет неизменяемый v1 `style-extractor`), enum `high|medium|low` и `null` (`anyOf`); экстрактор не меняется (§0.3).
- D-17 — при одновременных `cancel_requested` и `finalize --reason`: терминал `cancelled_by_user` (воля пользователя важнее служебной причины).
- D-18 — валидатор ревью проверяет `approved ⇒ 0 blockers` (одна сторона); `needs_revision` с 0 blockers (только major/minor) валиден. `unverified_hard_fail`: severity `blocker`, category `unverified_hard_fail`, `section_id: "document"`.
- D-19 — медиатор решается веткой 6 `revision next` (§4.5 п.4.6), а не до него; формулировка §2.1 стр.13 читается как «[медиатор при необходимости]».
- D-20 — `conflict` = две issues одного `(section_id, category)` с Jaccard ≥0.8 и противоположной полярностью отрицания; не сливаются, обе помечаются `conflict: true`.
- D-21 — `final_status_reasons[]` enum: `incomplete_review | all_reviewers_failed | regression_forced_exit | unresolved_blockers | no_checked_draft | length_overflow | lint_not_converged`; `length_overflow` ставит `revision next` на любой ветке выхода при наличии L-10 в актуальном `lint.json` (Brief) и перекрывает `approved_on_v<N>`.
- D-22 — severity lint: структура/провенанс/freeze (L-05/06/07/08/09/11/12/14) — blocker; L-01/02/04/10/13 — major; L-03 — minor; `clean` = нет blocker. L-06 для executive-brief: каждая аналитическая подсекция имеет ≥1 пункт Recommendations (сквозные пункты допустимы).
- D-23 — якоря секций: H2 → `<!-- §s-N -->`, H3 → `<!-- §s-N-M -->` (единая позиционная схема `draft anchor`); `section_id` во всех артефактах — эти же значения.
- D-24 — `quote extract --max-words` по умолчанию 30 (`limits.QUOTE_DEFAULT_MAX_WORDS`).
- D-25 — `Stop`-hook без стабильного ключа события: блокировки, записанные в пределах `STOP_GUARD_DEDUP_SECONDS=5` с, считаются одним Stop (варианты интерпретаторов не расходуют бюджет повторно).
- D-26 — `mf docs render permissions` пишет правило `Bash(${CLAUDE_PLUGIN_ROOT}/scripts/mf *)` (placeholder, не абсолютный путь), чтобы `docs/permissions.md` и `--check` были машинонезависимы; README поясняет, что пользователь подставляет путь.
- D-27 — версия плагина: единственный источник `.claude-plugin/plugin.json`; `scripts/memoforge/__init__.__version__` читает его (или равен ему буквально, с тестом идентичности).
- D-28 — `mf sources liveness|verify` и `mf docx validate` принимают `--step/--attempt` и закрывают свой шаг как все script-команды (completion-предикаты в `machine.py` для них убираются).
- D-29 — `test_idempotent_next_without_report`: повторный `next` по открытому dispatch возвращает тот же `step_id`/фазу без расхода бюджета и без продвижения (слоты без marker'а переиздаются с `attempt+1`, `reason: recovery`), полная байтовая идентичность не требуется.
- D-30 — `final_status_reasons[]` — список строк: документированные коды D-21 + машинные `intake_questions_invalid | plan_invalid | mcp_probe_invalid | writer_failed | cli_error | step_loop | interrupted`; свободный текст `finalize --reason` допустим; схема не навязывает enum.
- D-31 — в Brief `client-readiness-reviewer` запускается, polish отключён (`client_polish_enabled=false`).
- D-32 — повтор упавших ревьюеров: новый dispatch-шаг только для упавших kinds; `review aggregate` и `revision next` повторяются как тот же `step_id` с `attempt+1`, `reason: rerun`.
- D-33 — `mf deps check|install` реализуются модулем `scripts/memoforge/deps.py` (install: `pip install --target <plugin_data_dir>/site-packages -r requirements.txt`, только по явной команде).
- D-34 — текстовый ответ на гейт `gate-auq` поколения 0 (например `/memoforge:continue approve full`): `mf gate parse` сам увеличивает `generation`, пишет `gate_channel_switched`, затем парсит ответ — отдельный `report --status no_answer` не требуется (router описывает один путь).
- D-35 — `allowed-tools` фиксирован §3.4 только для `memo`; `style` сохраняет `Glob`/`Edit` (Task → Agent).
- D-36 — `mf task list --human` печатает таблицу (task_id, phase, mode, updated, work_dir).
- D-37 — `_meta {task_id, step_id, attempt, slot}` обязателен только в `research-findings` (в т.ч. `intake/preliminary-sources.json`); `intake/questions.json` без `_meta` (промпт аналитика сужается).
- D-38 — `client-readiness.checklist[]` остаётся опциональным в схеме; `machine.py` всегда передаёт чеклист — это допустимо.
- D-39 — `lint.json`/`citations.json` прикладываются ревьюерам только когда fix-раунды исчерпаны и драфт не lint-clean (`lint_not_converged`); в остальных случаях `lint_attachment` пуст.
- D-40 — `stepctx.check_identity` строгий: шаг обязан существовать в `steps[]`, `attempt` == текущему (иначе `identity_mismatch`); закрытая identity → сохранённый `result_ref`; **все** `--step`-команды (включая `docx render|validate`, `finalize`) проходят эту проверку до побочных эффектов и повторно под `state.lock` перед закрытием. Единственная реализация publish/close — `stepctx` (`publish_file`, `close_step`); `review.py`/`docx`/`finalize` используют её.
- D-41 — потребители канонических файлов читают их через `stepctx.read_published(work_dir, rel_path)`: sha файла == `published[]`, иначе `output_modified_after_publish` (→ recovery). Относится к `reviews/*.json`, `research/*.json`, `research/currency.json`, `research/source-pack.json`, драфтам.
- D-42 — `stage_input` сохраняет вход один раз на identity (`steps/<step>/a<n>/cli/inputs/`), повтор не перезаписывает; replay преобразующей команды пересчитывает из сохранённого входа и сравнивает с canonical.
- D-43 — `cli.main` пишет ровно одно событие `cli_call {group, cmd, ok, bytes_out}` на вызов при известном `--workdir` (в т.ч. no-op и ошибки); эмиссии `cli_call` из отдельных команд удаляются. `bytes_out` для `next` = длина ответа — источник G1.
- D-44 — `length_overflow` применяется на любом выходе цикла в `client_readiness` (ветки 2, 4, 5, 7, 8).
- D-45 — `analyze` не использует v1-поля (`aggregate_score`, `verdict`, `blocking_count`); регрессия берётся из `final_status_reasons` / `iterations[].substance_blockers` v2.
- D-46 — `ruff.toml` (`line-length = 120`, `target-version = "py39"`, правила E/F/W) — часть CI (§9); файл добавлен к §0.4.
- D-47 — README держит permissions-блок в `<details>` компактно; канонический построчный вид — `docs/permissions.md`.
- D-48 — описание в `schemas/state.schema.json` не должно называть удалённые ключи буквально (перефразировать «два ключа config, удалённые в v2»), чтобы `test_no_legacy` не нуждался в исключении.
- D-49 — суд/год/издатель/дата для OSCOLA-форм не расширяют закрытые схемы: рендерер выводит их из `identifiers` (ECLI/neutral citation) и из открытого `meta` (`court`, `year`, `issuing_body`, `date`, `short_name`); `legal-researcher` при `sources register --meta` передаёт эти ключи, когда они известны из ответа инструмента.
- D-50 — `finalize` переиспользует существующий `memo-<slug>.docx` только если `rendered_source_sha` совпадает с версией, выбранной `select_draft`; иначе — md-ветка/повторный рендер (та же привязка, что для markdown; §2.1 стр.15).
- D-51 — `docx validate`: любой литерал `[unresolved:` в любой части → `valid: false` и деградация в md (баннер не делает исключения); отсутствие `footnotes-map.json` — ошибка валидации, а не пропуск проверок.
- D-52 — `mf probe dry-run`: `ok: false` (провал инвариантов, `final_phase ≠ done`, непустой `g2_exceeded`) → `errors[]` в ответе и exit 1; CI проверяет exit code.
- D-53 — `no_change`-семантика применяется только к выходам `memo-writer` (сравнение с seed); для остальных агентов совпадение байтов с прежним canonical — нормальный `ok`. Порядок в `report` и autoclose одинаков: acceptance-проверки → публикация; `fail` не публикуется.
- D-54 — после изменения байтов драфта (writer fix/revision/polish) шаги `draft lint`/`draft audit-citations` переиздаются тем же `step_id` с `attempt+1`, `reason: rerun` (бесплатно); завершённая проверка привязана к `draft_sha` входа.
- D-55 — `reviewer_json_retry` учитывается по каждому провалившемуся kind отдельно (`<iteration>:<kind>`), владелец списания — `review aggregate`; retry-dispatch восстанавливает **полный** исходный spec из `steps[]` (сохраняется `spec` целиком), меняя только identity/пути/ошибки.
- D-56 — гейт плана: `approve` только при явном ответе `Plan`; пустой/частичный ответ → `errors`, не approve; смешанный `1A 2C 3: text` парсится целиком, частично распознанный ответ не коммитится.
- D-57 — `render` md-views (`research`, `currency`, `source-pack`, `mediator`, `sufficiency`) — обязательные script-шаги перед потребителями (writer, reviewers, gate 11); после polish с findings — один writer fix + lint/citations перед повтором readiness (§2.1 стр.14).
- D-58 — переиздание script-шага с `reason: rerun` требует изменившихся входов: `script_step` пишет `inputs_sha` в `steps[]` при выдаче и сравнивает при планировании (lint/citations — драфт и его отчёт, `docx validate` — docx и `footnotes-map`, render-views — исходный JSON); закрытый шаг с прежними входами считается выполненным. Закрытым считается любой статус, кроме `fail`: `skipped` — законный исход script-шага (`docx validate` без docx, D-51/M9). Общий страж: один `step_id` выдаётся не более `limits.MAX_STEP_ATTEMPTS = 8` раз, дальше — `finalize --reason step_loop` (код в списке D-30).
- D-59 — (15a N-01) публикация выхода писателя в autoclose-ветке (`resume_dispatch` → `close_step`) ведёт ту же бухгалтерию драфта, что и `report` (`_record_draft_publication`: `current_draft_path/sha`, `draft_versions[]`, `current_iteration`); единый путь для обоих каналов закрытия. Тест: writer-диспатч закрыт через `next` без `report` → прогон заканчивается `approved_on_v1`.
- D-60 — (15a N-02) `sync_draft_versions` читает `lint.json`/`citations.json` только через `stepctx.read_published`; дрейф файла = отчёт отсутствует (`lint_clean`/`citations_clean` = false). Прямых `read_json` канонических файлов в `machine.py` не остаётся (D-41).
- D-61 — (15a N-03) `gates.parse_reply` получает число напечатанных вопросов (`question_count`); ключ вне `1..N` → `errors: ["unrecognized_token"]`, `recognized: false`, коммита нет (D-56). `gate parse` и `report --answers` передают N из state/spec гейта.
- D-62 — (15a N-04, амендмент D-57) обязательные md-views: `render research` (входы writer) и `render mediator` (writer в revision получает путь `.md`, `.json` остаётся источником истины в state). `render sufficiency`, `render source-pack`, `render currency` машиной не выдаются (потребителя нет; текст гейта 11 строит `sources.render_digest`). Команды `render` в CLI сохраняются.
- D-63 — (15a N-05) кап `script` в G2 (dry-run) = **20** (`probe.G2_LIMITS`, §0.2): чистый маршрут после D-62 ≈13, запас на lint-fix (+2) и одну итерацию ревизии (+5). Шаги не объединяются (разные identity/`inputs_sha`, D-58). Dry-run дополнительно печатает оценку наблюдаемой метрики `g2_observed_estimate = next+report+script+gate+step_issued` с капом 150; §0.2 помечает, что колонка dry-run описывает чистый маршрут.
- D-64 — (15a N-06) `finalize`, не сумевший записать терминальную фазу (`_write_terminal` → `state_error`), возвращает `errors: [state_error]`, exit 1; страж `step_loop` для `finalize` остаётся выключен, recovery — общий `retry_failed_script` (один повтор → `transition("failed")`).
- D-65 — (15a N-07) остаток `reviewer_json_retry` читается по конкретному `<iteration>:<kind>`, без `max()`; `failure_attempts` для ревьюеров считается по `(iteration, kind)`, а не по `step_id`, чтобы `rerun_reviewers` с новым `step_id` не обнулял счётчик.
- D-66 — (15a N-08) текстовый ответ гейта плана с `edit:` сохраняет одновременно распознанные `Mode/Style/Sources`; forced approve берёт `Mode` из последнего распознанного ответа, иначе из state, и никогда не сбрасывает в `full` молча.
- D-67 — (15a N-12) `router.md`: «act on kind» относится к выдаче гейта (показу AskUserQuestion); текст пользователя в чате при открытом гейте любого вида идёт только через `mf gate parse … --generation <g>` (для `gate-auq` поколения 0 команда сама переключает канал, D-34) — никаких повторных промптов и ручных AUQ-ответов.
- Отклонено (15a): N-09 инкрементальный `build_progress` — журнал короткий, O(n²) при n≈100 незаметно, инкрементальные счётчики добавляют состояние для синхронизации; over-eng п.2 (`canonical`↔`canonical_path`), п.3 (`purpose` вместо `command_signature`), п.5 (удаление `review mediator-from-issues`, команда в §5 ТЗ) — рефакторинг рабочего кода без дефекта, откладывается до после релиза. N-11 (дубль ветки деградации) — принято, объединить.
- D-68 — (Codex b3r2 R2-01) `sync_draft_versions`: дрейф/отсутствие опубликованного `lint.json`/`citations.json` **отзывает** соответствующую отметку (`lint_clean`/`citations_clean` = false) у всех версий, а не пропускает файл; отчёт применяется только к версии с совпадающим `draft_sha`. Тест: проверенная версия → подмена отчёта → sync → экспорт не выбирает её как checked.
- D-69 — (R2-02) один JSON-retry на `(iteration, kind)` суммарно: `review aggregate` учитывает failure-попытки, уже выданные машиной для той же пары (единая функция подсчёта из `steps[]`, живёт в `review.py`, `machine.py` её импортирует; без циклического импорта). Итог: initial + не более одного повторного диспатча, затем stub. Тест считает реальные диспатчи.
- D-70 — (R2-03) forced approve плана: `Mode` = последний явно распознанный `Mode` в истории `plan_approval.iterations[].answers`, иначе `state.mode`, иначе `full`; тест через `plan_plan_approval_pending` с `state.mode="brief"` и исчерпанным `plan_edit`.
- D-71 — (R2-04) ключ нумерованного ответа нормализуется `str(int(key))` до проверки диапазона и сохранения (`01A` ≡ `1A`), одинаково для буквенных и свободных ответов.
- D-72 — (R2-05) ответ `gate parse` с `reprompt` — бизнес-исход, не ошибка CLI: router/SKILL печатают `reprompt` и завершают ход; правило «повторить один раз → `finalize --reason cli_error`» относится только к ответам без `reprompt` (технические ошибки). `gate_parse_errors` считает только непонятые ответы пользователя.
- D-73 — (17a R-03) в §0.4 добавляется `.claude-plugin/marketplace.json` (минимальный манифест одного плагина: `name`, `owner`, `plugins[{name, source: "./", description, version}]`), чтобы `/plugin marketplace add gregmos/memoforge` работал; zip для Cowork создаётся на шаге релиза (не в дереве).
