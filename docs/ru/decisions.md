# Архитектурные решения

[Указатель](README.md) · [Оригинал](../decisions.md). Перевод документации v2.0.0.

Краткие записи решений, определяющих архитектуру memoforge v2. Каждое решение ссылается на раздел [ТЗ](../TZ-memoforge-v2.md): ТЗ определяет требования, этот документ объясняет причины. Вопросы реализации отражены в [dev/IMPL-DECISIONS.md](../dev/IMPL-DECISIONS.md).

---

## ADR-01 — Процессом управляет код, содержательные решения принимают агенты

**Статус:** принято (v2.0-dev) · **ТЗ:** §1, §3, §13 · **Инварианты:** M1, M3

В v1 модель-оркестратор читала примерно 95–110 тысяч токенов инструкций за Full-запуск и всё равно пропускала шаги. В девяти из двенадцати зафиксированных инцидентов был пропущен служебный шаг. После каждого такого случая добавлялись инструкции, которые снова терялись при сжатии контекста. v2 переносит переходы между фазами, счётчики, лимиты повторов, выбор агентов и все записи состояния в `scripts/memoforge/`. Оркестратору остаётся протокол `next → act → report` примерно на 150 строк. Содержательные оценки остаются у агентов. После сжатия контекста для восстановления достаточно одного вызова `next`. Единственная оставшаяся зависимость от текста — инструкция самого протокола; поэтому она намеренно короткая, а операции идемпотентны.

## ADR-02 — Python-пакет; пилот Workflow за флагом

**Статус:** принято (v2.0-dev) · **ТЗ:** §3.2, §5, §10

Workflow позволяет передать управление процессом скрипту, но его работа из плагина не подтверждена во всех целевых средах. Полный переход привязал бы v2 к непроверенной возможности приложения. Поэтому поставляется обычный Python-пакет, запускаемый через навык-маршрутизатор. Границы сегментов S1–S4 позволяют в будущем передать отдельный сегмент Workflow без изменения его устройства. Каталог `workflows/` не объявляется до успешной проверки P1; пилот после неё охватит только S3a и S4. Решение обеспечивает переносимость и тестируемость, сохраняя модель в роли оркестратора.

## ADR-03 — Встроенные сигналы прогресса и необязательная страница

**Статус:** принято (v2.0-dev) · **ТЗ:** §7.1, §7.2, §7.5 · **Инвариант:** M7

По записи автора, отключение Cowork Live artifacts 19 августа 2026 года вывело из строя весь механизм прогресса v1: HTML-рендерер, обновления артефактов, widget MCP и 15 разделов «Live progress» в инструкциях агентов. v2 использует то, что уже показывает среда: `description` вызова `Agent` (`P<n>/<N> · agent · label`), строку чата на шаг, хуки журнала `events.jsonl`, `subagentStatusLine` и последующий анализ `mf events analyze`. Обязательная работа оркестратора для прогресса сокращается с 10–12 действий до одной строки (G8).

Необязательная страница реализована через `Artifact` и базу данных страницы (§7.5, D-87): одна публикация, далее по одному `write_db` на шаг. Эта историческая запись описывает исходное решение держать её выключенной до P3. После частично успешной P3 настройка включена по умолчанию (D-92); актуальные настройки приведены в [README](../../README.md).

## ADR-04 — Бинарные чек-листы и детерминированная агрегация

**Статус:** принято (v2.0-dev) · **ТЗ:** §4.5, §13 · **Инвариант:** M10

v1 запрашивала у пяти рецензентов общую оценку `overall_score` и завершала цикл при плато Δ<1,0. Такая граница находилась внутри примерно 13,6% изменчивости решения LLM-судьи: цикл колебался, а аварийный отчёт с нулевой оценкой мог вызвать ложный откат из-за «регрессии». В v2 у каждого рецензента фиксированный бинарный чек-лист (`LOG-`, `FRM-`, `CIT-`, `CTR-`, `CRD-`), проверяемый `mf review validate`. Код агрегирует результаты. Проверки структуры и ссылок выполняются до передачи черновика рецензентам. Максимум — две итерации; вторая нужна только при обоснованных блокирующих замечаниях. Сигнал менее подробный, но итог существенно стабильнее.

## ADR-05 — python-docx с прямой работой с OXML

**Статус:** принято (v2.0-dev) · **ТЗ:** §5.5

Нужны настоящие сноски Word (`footnotes.xml`, `w:footnoteReference`), сокращённые ссылки OSCOLA и перезапуск нумерации списков. python-docx не предоставляет эти возможности напрямую; их можно реализовать несколькими десятками строк OXML поверх библиотеки. Node и docx-js добавили бы вторую среду выполнения к Python-плагину, который должен работать на обычной Windows-машине. v2 преобразует AST `mistune` через python-docx, создаёт сноски через OXML и проверяет результат командой `mf docx validate` и эталонными тестами `document.xml`. Резервный Markdown на стандартной библиотеке обязателен: отсутствие `python-docx` не должно оставлять пользователя без результата (M9).

## ADR-06 — Системные блокировки файлов

**Статус:** принято (v2.0-dev) · **ТЗ:** §2.2, §7.2 · **Инварианты:** M2, M6

Параллельные агенты и повторяющиеся вызовы хуков пишут в один каталог. Поэтому `state.json`, `sources.json` и `events.jsonl` нужны взаимные блокировки, которые переживают аварийное завершение процесса. v2 использует `fcntl.flock` на POSIX и `msvcrt.locking` на Windows с постоянным файлом блокировки. Порядок захвата фиксирован: `state → sources → events`; он проверяется во время работы. Запись идёт через временный файл и `os.replace`. Файл-маркер вместо системной блокировки отклонён: после сбоя он остаётся и требует эвристики устаревания. Блокировки между машинами не поддерживаются; сетевая папка с двумя работающими компьютерами вне области задачи. Поддерживается одна платформенная развилка.

## ADR-07 — Lessons Studio отложена; техническое препятствие устранено

**Статус:** отложено (v2.0-dev) · **ТЗ:** §0.3 · **Инвариант:** M1

Обучение между запусками удалено в v1.0.0: все механизмы его поддержки существовали только как инструкции в `SKILL.md` и одновременно отказали в четырёхчасовом запуске. Условием возврата был механизм обеспечения, не зависящий от инструкций в контексте модели. v2 создаёт такую основу: машина состояний в коде, `events.jsonl`, гарантированный конечный шаг `mf finalize`, хуки Stop и SessionStart. Но функция остаётся за пределами v2.0 по правилу минимализма §0.3a: поставляются только механизмы, закрывающие зафиксированный инцидент или метрику G. К вопросу можно вернуться после измерения G1–G10 на реальных запусках.

## ADR-08 — Объём пакета в пять раз выше оценки §0.3a; это принято

**Статус:** принято (v2.0-dev) · **ТЗ:** §0.3a · **Решение:** D-80

Оценка §0.3a составляла примерно 3–3,5 тысячи строк Python и 2,5 тысячи строк тестов. Получилось примерно 18 и 17,6 тысячи соответственно. Причина — неверная оценка, а не расширение задачи: ТЗ требует 15 планировщиков фаз, 14 правил проверок, рендерер OSCOLA с настоящими сносками, фиксацию источников, идентификацию и повтор шагов, 19 схем, тестовый прогон и восемь ветвей доработки. По отдельности механизмы небольшие; каждый обязателен. Объём принят без сокращения перед 2.0.0. Правило минимализма продолжает действовать для новых механизмов. Кандидаты на сокращение после выпуска названы в ревью 17a: `mf sources slice` и неиспользуемая передача `config.*`.
